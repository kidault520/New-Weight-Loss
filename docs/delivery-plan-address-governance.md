# 配送计划与配送地址治理说明（v1.0）

## 1. 文档目的

本说明用于统一用户端、管理后台、配送执行链路在「配送计划 + 配送地址」场景下的规则、流程与风险控制，目标是：

- 降低错配、漏配、误删、误改风险
- 保证前台、后台、三方运力回传的一致性
- 在安全前提下保持用户操作简单、快速、可理解

---

## 2. 业务背景与风险特性

配送计划属于高风险模块，具有以下特点：

- **强时效**：配送前后窗口不同，规则需严格切换
- **强一致**：地址与计划需跨端同步，不能出现口径分裂
- **强反馈**：状态需实时/准实时更新，避免用户误判
- **高并发变更**：用户、后台、三方回调都可能同时改同一条数据

典型风险包括：

- 临近配送误改地址，导致配送失败
- 历史餐次被错误回写，导致审计混乱
- 删除在用地址，造成计划悬空
- 页面缓存或刷新机制不足导致“看见旧数据”

---

## 3. 核心实体与口径

## 3.1 核心实体

- `delivery_addresses`：地址主档（用户维护）
- `delivery_schedules`：配送计划明细（执行主档）
- `orders`：订单状态主档（服务中/已支付等）

## 3.2 单一真相（Source of Truth）

- 执行层：以 `delivery_schedules` 为准
- 地址信息来源：以 `delivery_address_id` 关联地址主档为主，快照字段为兜底

## 3.3 关键字段

- 地址关联：`delivery_address_id`
- 地址快照：`delivery_address` / `delivery_address_label` / 联系人 / 电话
- 时间：`delivery_date` + `delivery_time_start/end`
- 锁定：`is_locked`
- 履约状态：`status`
- 三方回传辅助：`delivery_provider` / `external_order_id` / `rider_*` / `delivered_at`

---

## 4. 当前生效规则（必须遵守）

## 4.1 地址编辑规则

1. 过去日期餐次：不可修改  
2. 今天且进入配送前 1 小时窗口：不可修改（硬拦截）  
3. 未来餐次：可修改  
4. 地址已在计划中使用：编辑前必须二次确认  
5. 地址删除：先校验是否在用，在用则直接“无法删除”提示

## 4.2 地址回写规则（地址主档更新后）

仅允许回写以下计划记录：

- `delivery_date >= 今天`
- 且状态属于可执行态（`pending/scheduled/preparing/shipped`）
- 且今天记录未进入“配送前1小时锁定窗口”

明确不回写：

- 过去餐次
- 已锁定窗口内的今天餐次
- 已完成/已取消记录

## 4.3 计划确认后的交互顺序

确认配送计划成功后，必须执行：

1. 当前流程内先弹“配置已生效”
2. 用户点击“知道了”
3. 再跳转到餐食页面

禁止顺序：先跳页面，后弹窗。

## 4.4 后台展示规则

- 过期配送计划整行灰化
- 显示“配送反馈状态”列：`已配送完成/配送中/即将配送/待配送`
- 支持自动刷新 + 立即刷新按钮 + 最近刷新成功时间
- 分组规则：同用户 + 同订单号

---

## 5. 端到端流程（用户视角）

## 5.1 新建配送计划

日期选择 -> 餐次确认 -> 地址选择 -> 配送计划确认 -> 生效弹窗 -> 餐食页面

## 5.2 修改地址

点击编辑 -> 编辑前守卫校验 ->  

- 命中今日锁定窗口：直接阻断  
- 在计划中使用：二次确认后进入编辑  
- 其余：直接进入编辑

保存后：主档更新 + 合法范围内计划回写 + 前后台同步刷新。

## 5.3 删除地址

点击删除 -> 先判是否在用 ->  

- 在用：直接提示不可删  
- 不在用：弹确认 -> 删除

---

## 6. 状态口径与映射

## 6.1 内部状态（执行状态）

- `pending` / `scheduled` / `preparing` / `shipped` / `delivered` / `cancelled`

## 6.2 后台配送反馈状态（展示态）

- 已配送完成：`delivered` 或有 `delivered_at`
- 配送中：`shipped` 或存在骑手信息/骑手定位更新
- 即将配送：`scheduled` 或 `preparing`
- 待配送：其他可执行态
- 已取消：`cancelled`

说明：展示态用于人读，不替代执行态。

---

## 7. 数据一致性机制

## 7.1 已实现机制

- 地址编辑前守卫（锁定窗口 + 在用确认）
- 地址删除前校验（在用即拦截）
- 地址回写按时间与状态过滤
- 后台自动刷新 + 手动刷新
- 前后端时间计算改为本地日期口径，减少时区错位

## 7.2 建议补齐机制（按优先级）

### P0（必须尽快）

1. 增加 `locked_at` 独立字段（避免 `updated_at` 污染锁定时间）  
2. 增加审计日志（谁在何时改了哪条餐次）  
3. 增加并发冲突控制（版本号或 `updated_at` 乐观锁）  
4. 三方回调幂等保护（同事件多次到达不重复更新）  
5. 定时对账任务（回传失败/丢包后自动校正）

### P1（强烈建议）

1. 修改影响范围提示（影响 N 天/N 餐次）  
2. 锁定倒计时提示（距离锁定 xx 分钟）  
3. 软删除地址（历史可追溯）  
4. 地址变更后消息提醒（防“修改后遗忘”）

### P2（体验增强）

1. 30 秒撤销窗口  
2. 修改前后差异对比  
3. 后台异常看板（锁定冲突、状态停滞、回调失败）

---

## 8. 失败与异常场景处理

## 8.1 网络/接口失败

- 前端提示“同步失败，请重试”
- 不做静默吞错
- 保留用户当前输入，不强制回滚页面

## 8.2 并发覆盖

- 检测到版本冲突时，提示“数据已变更，请刷新后重试”
- 禁止直接覆盖最新记录

## 8.3 三方状态延迟

- 列表保留“最近同步时间”
- 超过阈值未更新进入“状态待确认”提醒

---

## 9. UI/交互红线

- 锁定窗口内必须显式不可编辑（灰态 + 锁图标 + 文案）
- 过期计划必须灰化，禁止误导为可执行
- 高风险动作（改在用地址、删地址）必须先反馈影响再继续
- 所有关键反馈必须即时可见且可理解（避免“无感失败”）

---

## 10. 测试与上线验收清单

上线前必须全通过：

1. 过去餐次在所有入口不可修改  
2. 今日进入锁定窗口后不可修改  
3. 地址在用时删除直接拦截  
4. 地址编辑影响范围提示准确  
5. 计划确认后“先弹窗后跳转”  
6. 后台反馈状态与回传一致  
7. 过期计划整行灰化  
8. 用户端改动后台可在刷新窗口内可见  
9. 同时操作不发生无提示覆盖  
10. 关键操作可追踪（至少日志可查）
