# 语音自动确认与取消规范 v1.0

## 1. 目标

在聊天窗口中，用户使用明显肯定或否定指令时，系统可对当前待确认卡片执行自动确认或自动取消，减少重复点击成本，并保持“可追溯、可回滚、可解释”。

## 2. 适用范围

仅适用于“待确认卡片”与“卡片内明确动作按钮”，不扩展到支付、订单状态变更等高风险动作。

## 3. 基本原则

1. 自动执行只作用于“当前焦点卡片”。
2. 同时存在多张待确认卡片时，不做盲执行，必须先澄清目标。
3. 否定优先于肯定（例如“可以先不记录”应判定为取消）。
4. 低置信度语音不执行，保持现状并提示重说。
5. 所有自动动作都必须复用现有按钮对应的业务逻辑，不允许绕过校验直接写库。

### 4.3 冲突语句处理

若同一句出现肯定与否定词，按否定优先，并给出确认提示，例如“我理解为暂不记录，如需保存请说‘确认保存’”。

### 4.4 关键词匹配建议（避免误判）

1. 先做文本归一化：去标点、去语气词、全角半角统一、同义词归并（如“记一下/记录一下/记上”）。
2. 匹配优先级：强否定 > 强肯定 > 弱否定 > 弱肯定。
3. 命中弱词时不直接执行，先回问“你是要确认保存还是取消？”。
4. 出现范围词时不执行（如“都确认”“全删”），要求用户点名目标卡片。
5. 命中“支付/开单/开启服务/提交配送计划”等高风险词时，一律只提示手动点击，不自动执行。

### 4.5 语音执行置信度阈值（首版）

- 强匹配：置信度 `>= 0.80`，可直接执行。
- 弱匹配：置信度 `0.60 - 0.79`，必须先二次确认。
- 低置信度：`< 0.60`，不执行，仅提示“请重说确认或取消”。

建议将阈值做成可配置项，按灰度阶段逐步调整，不在首版硬编码到多个组件。

## 5. 组件动作规则表

| 组件/卡片 | 肯定语音动作 | 否定语音动作 | 默认动作 | 是否二次确认 |
|---|---|---|---|---|
| QuickEntryCard（单条待确认健康数据） | 确认并保存该条 | 取消/删除该条 | 保持不动 | 否 |
| DailyReportCard - 待确认数据单条 | 确认该条 | 取消该条 | 保持不动 | 否 |
| TodayMealsCard - 已摄入按钮 | 执行该餐已摄入 | 放弃本次摄入动作 | 保持不动 | 否 |
| TodaySupplementsCard - 已摄入按钮 | 执行该补剂已摄入 | 放弃本次摄入动作 | 保持不动 | 否 |
| 批量删除/批量确认类动作 | 不直接执行 | 不直接执行 | 先追问目标范围 | 是 |
| 支付/开启服务/配送计划提交 | 不直接执行 | 不直接执行 | 仅提示用户手动点按 | 是 |

## 6. 多卡片并存时的澄清策略

当待确认卡片数量 > 1 时，语音命中肯定/否定词后，统一进入澄清：

- “你要确认哪一条？我看到有 X 条待确认记录。”
- 支持用户回答“第一条/体重那条/刚刚那条”后再执行。

## 7. 执行反馈规范

自动动作执行后，必须发送明确反馈：

- 成功确认：已为你确认并保存[指标名]记录。
- 成功取消：已为你取消[指标名]待确认记录。
- 执行失败：本次操作失败，请手动点击重试。

## 8. 安全与审计要求

1. 自动执行与手动点击走同一业务链路（同一 service / mutation）。
2. 自动执行需写入行为来源标记（voice_auto_confirm / voice_auto_cancel）。
3. 禁止在语音判定未命中时“猜测执行”。
4. 禁止将“咨询类语句”误当确认指令执行写库。

## 9. 不执行场景

- 语义模糊（例如“嗯、好吧、随便”）。
- 语音识别置信度低于阈值。
- 当前没有可执行的待确认卡片。
- 目标卡片已完成或已失效。

## 10. 验收标准（首版）

1. 单卡片场景：肯定词命中后可自动确认，否定词命中后可自动取消。
2. 多卡片场景：不会误操作，先澄清目标。
3. 支付/订单/配送提交不会被语音自动触发。
4. 每次自动动作都有反馈文案，且可在日志中区分动作来源。
