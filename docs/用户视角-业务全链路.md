# 用户视角 · 业务全链路

> 本文从 **C 端用户**「看见什么、要点什么、期望发生什么」整理整条闭环，便于产品、客服与测试对齐口径。  
> **技术字段、表名、接口**仅作脚注式引用；实现细节见 **`业务总图+验收清单.md`**、**`order-flow-and-status.md`**。

---

## 1. 用户需要知道的前提

- **订单不是自己从商城里下单生成的**：一般是线下与销售沟通好后，由 **管理后台代为创建**。用户在 App 里看到的是「已经有一笔属于我的订单」。
- **支付在 App（或后台代录）完成**：支付只改变「钱是否付清」等状态，**不会**改掉订单上的顾问/销售归属（用户在订单里看到的顾问信息应与建单时一致）。
- **餐食有「契约餐次」**：用户只能按 **这笔订单包含的餐次** 配置配送，**不能**在 App 里自己多加一餐（避免与成交内容不一致）。
- **配送计划会落到系统里**：用户配置的日期、每餐送哪里，最终以 **配送排期** 为准；聊天卡片、配送计划页、订单侧应展示一致（具体入口见下文）。

---

## 2. 一条时间线：从「有订单」到「服务中」

下面按 **多数用户** 的主路径叙述；个别步骤若后台未启用（如财务确认），用户可能无感知。

| 阶段 | 用户感知 | 用户典型动作 | 系统应对（用户可见结果） |
|------|----------|--------------|---------------------------|
| **A. 订单已生成** | App 里出现待处理订单，状态类似「待支付」 | 打开「我的订单」或相关入口 | 展示订单金额、商品/疗程摘要、顾问信息等（以实际 UI 为准） |
| **B. 支付** | 需要付款才能继续后面流程 | 在 App 内完成支付；或由后台代录（用户侧仅看到已付） | 订单变为已支付；重复支付应有明确提示，不重复扣逻辑上的进度 |
| **C. 确认（若有）** | 多数情况下 **无单独页面** | 无需操作 | 若后台启用销售/财务确认，仅影响后台与后续校验；用户可能感觉不到 |
| **D. 开启服务 · 配置履约** | 提示去配置配送：日期、餐次、地址 | 点「开启服务」等入口 → 选配送日/排除日 → **只选订单内餐次** → 为每餐绑定地址 → 生成/确认配送计划 | 缺哪餐地址会 **明确拦截** 并提示缺什么；保存成功后计划应可回看 |
| **E. 进入服务中** | 订单显示「服务中」或等价文案 | 上一步流程走通并满足规则（已付 + 有餐食的需先有配送排期等） | 与后台「已开启」展示对齐；之后主要看每日配送与执行类内容 |
| **F. 履约期** | 看配送计划、打卡类任务、聊天里的今日餐/补剂等 | 按 App 各模块使用 | 纯 **补剂** 订单 **不应** 出现虚构的「整包健康餐」块；餐食则以契约餐次与排期为准 |
| **G. 结束 / 评价（预留）** | 周期结束或订单结束 | 若有评价入口则评价 | 以实际上线与字段为准 |
| **H. 退单（少数）** | 订单关闭、已退款等 | 通常由后台或客服发起；若 C 端有退单入口则按提示操作 | 用户侧看到订单取消/已退款；该单不再计入正常履约 |

## 3. 用户从哪些地方能碰到「配送 / 订单」

不同产品入口名称可能微调，逻辑上应对齐为 **同一套数据**：

- **我的订单**：列表与详情、支付、开启服务、状态标签。
- **配送计划**（含「我的」里入口、瑞丹维等若存在同构入口）：查看与修改 **未来可改** 的排期；锁窗、已送出当餐等规则下，部分日期/餐次 **不可改**，应有说明而不是静默失败。
- **聊天区卡片**（如今日配送、配送计划卡片）：展示应与配送计划页 **一致**；改某一餐地址时，常见交互为 **确认 → 短时「锁定中」→ 自动锁定**（与验收清单一致）。

**无有效订单时**：从上述入口进入应 **提示原因**，不应白屏或跳到错误流程。

## 4. 用户会遇到的「拦路」与正确预期

| 情况 | 用户应看到 / 应能做什么 |
|------|-------------------------|
| 未付清 | 开启服务或生成计划应被拦下，并说明需先完成支付 |
| 订单里有多餐，但只配了部分餐的地址 | **不能** 生成完整配送计划；提示 **缺哪几餐的地址** |
| 某一餐已到截单/锁窗或配送已开始 | 该餐在可编辑范围外；不因编辑其他餐误伤或误提示 |
| 重复点支付、网络重试 | 不应重复算「已付多次」；应有已支付或冲突类友好提示 |
| 保存了计划但未进入服务中 | 文案应区分 **「计划已保存」** 与 **「已进入服务中」**，避免用户误以为已开课/已起送 |

## 5. 与后台分工的一句话对照（仍站在用户侧）

- **后台负责**：建单、选顾问、商品/疗程配置、代录支付、退单、内部备注、运营查看与审计等。  
- **用户 App 负责**：看到自己的订单、支付、配置配送与查看履约相关展示；**不负责** 改订单上的商品、金额、顾问（这些建单后不可改）。
