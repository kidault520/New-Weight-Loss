# 上线差距清单（相对「真实可上线」）

本文描述**当前实现与可对外生产上线之间**仍存在的差距，用于评估工作量；**不按优先级排序**，排期由项目组自行决定。

**说明**：清单基于仓库代码与 `docs` 内既有说明整理；第三方账号、渠道审核、法务合规的人天因组织而异，需单独估算缓冲。

**关联文档**：`端到端业务与开发说明.md`、`AI聊天与反馈-标准说明.md`、`.cursor/rules/third-party-aggregation.mdc`。

---

## 1. 三方与通道

| 项 | 与上线差距（需补的工作） |
|----|-------------------------|
| 短信 OTP | 生产需 `SMS_PROVIDER=webhook`（或扩展服务）+ 可达的 `SMS_WEBHOOK_URL`、鉴权；聚合/自建网关的字段映射、失败重试、监控；生产禁止依赖 `mock`；若与 Supabase Auth 或自建 OTP 并存，需与频率限制、Redis OTP 等联调闭环。 |
| 支付（微信/支付宝等） | 后端具备回调与创建支付单能力骨架，但用户侧当前为 `confirm-payment` 模拟支付直改库。上线需：创建预支付单 → 前端唤起收银台/小程序支付 → 以支付结果回调为准（或聚合等价流程）；沙箱/生产配置分离；签名、幂等、对账与财务要求对齐。 |
| 配送运力 | 状态回调、webhook 下发、顺丰备选等有代码基础。产品顺序：**已付费 → 开启服务 → 配置配送计划（新址或历史地址）** 后再对运力生效；`createDeliveryOrder` 宜在 **计划与地址就绪** 后触发，而非支付回调瞬间。需确认：该触发点、异常重试、与 `delivery_schedules` 一致；运力侧订单号、状态枚举与 `deliveryStatusMapping` 等在生产验证。 |
| 地图选点 / 地址解析 | 用户端已接 **高德 JSAPI**：地图选点、逆地理回填 `address` 与 `longitude`/`latitude`（需配置 `VITE_AMAP_KEY` 并执行迁移 `delivery_addresses` 经纬度列）。配送范围校验、与运力字段对齐等可按业务再补。 |
| 微信登录 | `AuthContext.signInWithWeChat` 为未实现占位。需 OAuth/小程序登录方案、与 Supabase 或后端账号体系绑定、手机号合并/冲突策略。 |
| AI 大模型 | Edge `ai-chat` 等可调真实模型。需：Supabase Secrets 与代码中环境变量命名一致、配额与失败降级、各 Edge 函数分别部署与密钥；多模型/降级策略与成本监控（若需要）。 |
| 穿戴设备同步 | 多为列表/UI。需具体厂商或 HealthKit/Health Connect 等授权、同步任务、冲突解决、写入 `health_records` 并与日反馈/快照同源。 |
| 语音输入 | 仅有输入模式切换。需 Web Speech 或服务端 ASR、隐私与费用、与聊天输入对接。 |
| Push 推送 | 集成中心有配置项。需 Device Token 注册、服务端推送、与业务事件绑定（订单、配送、待办等），iOS/Android/Web 各自证书与通道。 |

## 2. 核心业务链路（目标态对照）

| 领域 | 差距 |
|------|------|
| 订单状态机 | `待支付 → 已支付 → 服务中/待配送` 等与 App、管理端、执行计划是否在全场景一致；取消、退款、超时未付等若产品需要则需补齐。 |
| B 端商品/套餐 | 商品、套餐、价格与订单行一致；后台录入权限与审计（若尚未满足）。 |
| 服务开启 / 开始时间 | `payment_time`、`start_time` 与北京日、计划天数/阶段/餐次一致；端到端校验。 |
| 地址与配送 | `delivery_addresses`、`delivery_schedules`、餐次绑定、锁单窗口；与三方「更严规则」并存时的产品与实现处理。 |
| 今日餐食 / 热量 / 日反馈 | 快照、库表、日反馈统计同源；设备与快捷卡片数据进入同一套统计的数据链闭合。 |

## 3. 前端/客户端仍含非生产数据或占位

| 位置 | 说明 |
|------|------|
| 配送计划 | `deliveryPlanService` 等处多日餐次仍可能使用固定拼装数据，需接真实排期/套餐数据源。 |
| 步数等 | 部分页面存在随机 mock 路径，需改为真实数据或明确隐藏。 |
| 其他业务页 | 若仍有「模拟数据」提示，需产品决定是否上线前替换或下架入口。 |
| 管理端集成中心 | 联调/评估/dry-run 不等于生产主路径已自动接通。 |

## 4. 认证、账号与合规

| 项 | 差距 |
|----|------|
| 登录路径统一 | Supabase Auth 与 Node `/api/auth` 需与前端约定单一事实来源，避免双轨。 |
| 微信登录 | 见 §1。 |
| 注销账号 | 产品若要求上线必备，当前文档记载为未闭环则需排期实现。 |
| 隐私与协议 | 地图、语音、设备、推送涉及权限说明与用户同意（视地区与上架渠道）。 |

## 5. 工程、部署与运维

| 项 | 差距 |
|----|------|
| 环境变量 | 前端 `VITE_*`、Node `server`、Supabase、Edge 配置完整且与示例/文档一致；密钥不进仓库。 |
| 数据库 | 生产迁移顺序与回滚；RLS/权限符合上线要求。 |
| 多进程/多入口 | 用户端、管理端、`server`、Edge 的部署拓扑、CORS、HTTPS、回调 URL 可达与白名单。 |
| 可观测性 | 日志、错误追踪、支付/配送回调失败告警；对账任务是否定时运行、失败可感知。 |
| 安全 | 回调 Token、JWT、Rate limit、防重放；管理端权限。 |

## 6. 测试与验收（上线前通常必做）

| 类型 | 内容 |
|------|------|
| 端到端 | 注册/登录 → 下单 → 真实支付沙箱 → 服务开启 → 地址 → 配送状态回写 → App 展示。 |
| 回归 | 订单状态、AI 聊天、日反馈、关键表单。 |
| 性能与弱网 | 登录与会话、慢请求等是否满足体验底线。 |

---

## 7. 结论（如何用于估工作量）

当前状态**不是**「基础功能均已就绪、仅差在管理后台填写三方 API」。更接近：**支付/配送/SMS 等已有聚合与回调骨架，但用户侧真实支付、配送与订单主流程自动化、地图、微信登录、设备、语音、Push 及多处业务数据仍需按生产标准补齐**。

估人天/人周时，建议对 §1～§6 **按产品必选范围逐项拆任务**，并单独加联调、审核与合规缓冲。

**维护**：重大模块上线或回滚后，更新 §1～§3；基础设施变更时更新 §5；验收标准变化时更新 §6。
