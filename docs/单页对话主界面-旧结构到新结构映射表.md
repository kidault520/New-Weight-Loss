# 单页对话主界面：旧结构 → 新结构 映射表

本文档将**现有页面/组件**逐一映射到「单页对话主界面」升级后的形态：  
**新形态** = 对话内卡片 或 抽屉/次级页；**触发入口** = 置顶卡片 / 对话系统消息 / 底部快捷条 / 顶部图标。

> **配套文档**：产品·架构·数据·通信·性能·AI·运营·三方配送的**全面检查与建议**见  
> `单页对话主界面-全面检查与建议（产品·架构·数据·通信·性能·AI·运营·三方配送）.md`  
> （目标规模：约 10 万用户、日 100 单；含三方运力打通建议。）

## 四点五、对话按天隔离（每天一结）与左侧抽屉

### 每天一结

- **策略**：每天进入聊天窗口都是**当天的对话**，不把全部历史堆在同一窗口，避免对话过长。
- **行为**：主界面中部对话区默认展示**今日**的消息与卡片；切换日期（通过左侧抽屉或顶部日期）时，加载并展示**该日**的对话流与待办卡片。
- **存储**：按日期维度存储与拉取对话消息与业务卡片（如 `chat_messages` / 卡片按 `date` 分区或查询）；重进 app 后默认进入「今日」窗口。

### 左侧抽屉（日历日记流）— 参考图 1 排版

- **位置与形态**：整个 app **左侧**滑出的抽屉（与右侧/底部业务抽屉区分），**版式与分区参考图 1**，卡片名称与内容为本 app 自有（不照搬参考图中的文案）。
- **顶部区域（用户与【我的】入口）**：
  - 左侧：用户头像 + 昵称。
  - 「**订单 · 设置**」或「**我的**」文案 + 右箭头，**点开即进入【我的】页**（见「二十三」及第五节），与之前独立 tab「我的」类似，做成全屏或大抽屉。
  - 右侧：**消息**、**任务中心**等图标入口（按产品需要保留）。
- **服务卡片区（紧接顶部下方）**：
  - **「服务套餐」卡片**（图 1 中类似位置为「医疗保障」，**仅排版借鉴**）：主标题「服务套餐」，副标题如「餐食 · 补剂服务」；点击进入**套餐汇总页**，整合展示当前周期**餐食 + 补剂**（配送计划、补剂方案、订单概览等），可与现有 MealPlan / CustomSupplement / 订单 能力整合。
  - **「健康档案」卡片**（图 1 同名为「健康档案」，**仅排版借鉴**）：主标题「健康档案」，副标题如「数据汇总与洞察」；点击进入**卡片汇总首页**（见「二十三」），即之前首页多张数据卡的完整版（今日洞察 + 健康仪表盘多卡 + 病历夹等），**不是**主界面对话上方的 3 张置顶卡。
- **最近使用（可选）**：横向滚动的「最近使用」入口（如某 AI、运动、饮食等），右侧「更多 >」。
- **对话记录（日历日记流）**：
  - 标题「对话记录」；下方按**时间分组**（如「最近 7 天」「2026 年」「2025 年」），每组内按日倒序，**每天一条**：左侧为当日聊天标记（主题/摘要），右侧为日期（「周x」或「x月x日」）。
  - 点击某一条 → 关闭左侧抽屉，主界面切换为**该日**的单日对话视图。
- **与主界面关系**：主界面顶部或左上提供**入口**（汉堡菜单/日历图标）打开该左侧抽屉；选中某日即切到该日单日视图；置顶 3 卡始终为「今日」。

### 单日聊天视图（某一天的对话流）

- **展示方式**：参考图 2 的**时间线 + 卡片**结构，用于**某一天**的聊天记录流。
  - **顶部**：当前日期（如「2月25日 周三」）固定展示。
  - **中部**：竖向时间轴（虚线或细线）+ 时间节点（如 待开始、07:30、08:00、12:00…）；每个节点下为该时间段的**消息/待办卡片**。
  - **卡片样式**：每条系统消息、用户消息或业务卡（配送、血糖、体重、待办等）以**圆角卡片**形式呈现，可含：图标、标题、简短描述、CTA 按钮（如「去完成」「查看详情」）；**配色与字体沿用现有 app 主体风格**，不采用图 2 的绿/蓝配色。
- **待办卡片 UI**：置顶「今日待办」及对话内的待办类卡片，可借鉴图 2 的**卡片布局**（图标 + 标题 + 描述 + 操作按钮），仅视觉风格（配色、圆角、间距）与现有 app 统一。

## 十二、推送与触发规则

以下为「何时推送哪张卡」的约定，便于实现与验收。

| 卡片/消息类型 | 触发时机 |
|---------------|----------|
| **配送确认卡** | 在**送餐前 ≥1 小时**推送当餐配送信息卡（含可改地址/时间的截止倒计时）；若已不足 1 小时，只推只读状态卡并说明「已过修改截止时间」。 |
| **餐后血糖卡** | 在**用户确认「开始用餐」或系统默认（如送达后 15 分钟）起的 30 分钟后**推送；若已接入 CGM，卡片自动带 CGM 数值，否则展示「手动记录」入口。 |

| **周报** | 每周固定日（如周日）推送「本周报告」摘要卡。 |
| **项目总结** | 周期/项目结束时推送「项目总结」卡。 |
| **补剂提醒** | 若存在补剂计划，在当次服用时间点推送补剂提醒卡（可带「已服用 / 暂缓」）。 |

## 二十、其他补充约定

以下为通读文档后的补充，避免实现时产生歧义或遗漏。

### 置顶卡与「当前选中日期」的关系

- **约定**：置顶 3 卡（今日待办、今日指标、阶段进度）**始终展示「今日」**的数据。
- **当用户从左侧抽屉选择某历史日**时：仅**中部单日对话视图**切换为该日；置顶卡仍为今日，不随选中日变化。这样避免「昨天待办」与「今日指标」混在一起，实现也更简单。
- 若产品后续希望「选昨天也看昨天的待办/指标」，可再单独扩展。

### 左侧抽屉与业务抽屉的关系

- **互斥**：左侧抽屉（日历日记流）与右侧/底部业务抽屉（我的、设置、报告、地址等）**不同时打开**。打开任一侧抽屉时，先关闭另一侧，避免多层抽屉叠加、返回键逻辑混乱。
- **左侧抽屉顶部入口**：若放置「订单、设置」等，可与「我的」抽屉内入口复用（点击后关闭左侧抽屉，再打开对应业务抽屉）；若担心入口重复，左侧抽屉可只保留「日历日记流」主体，顶部仅保留「关闭」或品牌区。

### 聊天标记与空状态

- **当日无对话/无记录时**：左侧抽屉该日条目可展示为「今日无对话」或系统默认文案（如「配送 · 打卡」）；单日视图内无消息时，展示简短引导（如「今日暂无记录，从下方开始吧」）+ 置顶卡，与「首次进入新首页」空状态一致。
- **聊天标记数据来源**：左侧抽屉列表需要「每日一条」的摘要。实现时需确认：按日存储的消息/卡片是否支持「取当日首条或系统生成摘要」供列表展示；若无现成接口，需在写入或日结时生成/写入每日摘要字段。

### 实施阶段与「每天一结 + 左侧抽屉」的落位

- **建议**：**每天一结**（按日加载对话）与**左侧抽屉（日历日记流）**在 **Phase 1** 与单页主界面一并落地，否则无法「按日切换」单日视图，后续再补会牵涉状态与数据较多。Phase 1 可先实现「今日 + 左侧列表 + 点击某日切到该日单日视图」的最小闭环，再在后续 Phase 完善推送、报告等。

### 跨天未读

- 若用户某日未点「今日总结」或某条推送，次日进入为「今日」窗口，该条留在昨日对话中。可选：在今日首条系统消息中弱提示「昨日还有未读内容，可到左侧选择昨日查看」，不强求。

## 二十二、文档新增内容与可能的新增板块/字段

以下为本次改造**新增**的形态或逻辑，且可能涉及**新增数据表、字段或接口**，便于实现时评估。

### 1. 左侧抽屉「每日聊天标记」列表

- **现状**：现有 app 无「按日列表 + 每日一条摘要」的入口；`chat_messages` 仅有 `created_at`，可按日期范围查询，但无「当日摘要」字段。
- **需要**：左侧抽屉需展示「每日一条」的聊天标记（标题/摘要 + 日期）。
- **建议实现**（二选一或组合）：
  - **方案 A**：不新增表，列表展示时用「当日首条 user 消息的 content 截断」或「当日第一条系统消息的标题」作为标记；无消息的日期不展示或展示「今日无对话」。
  - **方案 B**：新增表 `chat_daily_summaries`（或等价）：`user_id`、`date`（仅日期）、`summary_text`、`created_at`；在当日首条消息写入或日结时生成/更新该日摘要，左侧抽屉读该表。
- **结论**：若采用方案 B，需**新增表或等效存储**；方案 A 无需新表，仅前端或现有 service 按日聚合首条即可。

### 2. 按日加载对话（每天一结）

- **现状**：`chat_messages` 已有 `created_at`；`chatMessagesService.getMessagesByDateRange` 已支持按时间范围查询。
- **需要**：按「自然日」（用户时区 0 点至 24 点）查询当日消息并展示；重进 app 默认「今日」。
- **结论**：**无需新表/新字段**；需在 service 或 hook 层提供「按日」查询（如 `getMessagesByDay(userId, date)`），并对接单日视图与左侧抽屉选中日。

### 3. 业务卡片在对话中的持久化

- **现状**：`chat_messages` 已支持 `message_type = 'quickEntry'` 及 `quick_entry_data`（jsonb）、`is_quick_entry_confirmed`，可存一种卡片。
- **需要**：配送卡、血糖卡、报告卡、待办卡等多种**结构化业务卡片**需出现在对话流中并可持久化、按日加载。
- **建议**：要么扩展 `message_type` 与 payload（如新增 `delivery`、`blood_glucose`、`report` 等，并用 jsonb 存卡片数据），要么新增一张「对话内卡片」表（如 `chat_message_cards`：`message_id`、`card_type`、`card_data`），与 `chat_messages` 关联。若沿用「一条消息对应一张卡」，扩展 `chat_messages` 的 type + 一个通用 jsonb 即可，**无需必选新表**；若希望消息与卡片一对多，再考虑卡片表。

### 4. 其他

- **置顶 3 卡、底部能力条、单日时间线 UI**：均为前端展示与入口调整，数据来源仍为现有表（执行计划、配送、健康记录、报告等），**无需新增表/字段**。
- **推送与触发规则**：若由后端或定时任务推送，需在现有推送/任务配置中增加「按规则推送」的逻辑，不必然新增表；若要做「推送记录」可另表存储，按现有架构决定即可。

- **完整「卡片汇总首页」**：从**左侧抽屉**里的**「健康档案」卡片**进入，打开**健康档案页**（**版式**参考图 4；具体卡片类型与文案为本 app 现有，如体重、血糖、睡眠、步数等）：
  - 顶部：返回 + 标题「健康档案」+ 设置/入口；
  - 可选**用户/档案切换**（如多成员时 彭*、余* + 添加）；
  - **今日洞察**：当日一句洞察或建议；
  - **健康仪表盘**：多张数据卡（睡眠、步数、运动、饮食、热量、站立等），即之前首页 Dashboard 的完整卡片网格；
  - 底部：Tab「健康数据」+ **中间的「+」**（见下）+「病历夹」等。
- **结论**：想看「之前首页那么多卡片汇总」→ 打开左侧抽屉 → 点「健康档案」→ 进入图 4 式的卡片汇总首页；主界面只保留 3 张置顶卡。

### 3. 服务套餐（餐食 + 补剂）如何整合（图 1 仅排版参考）

- 在**左侧抽屉**内，与「健康档案」并列放一张**「服务套餐」**卡片（图 1 中类似位置为「医疗保障」，**仅版式借鉴**）：主标题「服务套餐」，副标题「餐食 · 补剂服务」或类似。
- **点击该卡片**进入**套餐汇总页**（或一层聚合页），内可包含：
  - 当前周期/订单概览；
  - **餐食**：配送计划、今日餐单、课表、修改配送入口；
  - **补剂**：补剂方案、服用提醒、CustomSupplement 入口；
  - 订单/续费入口等。
- **结论**：餐食与补剂整合在「服务套餐」一个入口下，从左侧抽屉进入，不再依赖主界面底部原「套餐」tab。
