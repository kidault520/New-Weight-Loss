## 1. 入口矩阵（从哪里进、无权限/无数据如何表现）

| 入口 | 代码/组件 | 无会话（未登录） | 无档案/无数据 | 备注与风险 |
|------|-----------|------------------|---------------|------------|
| 登录 | `LoginPage.tsx` | 展示登录表单 | — | 见 §4：「发码」为**本地模拟**，未接真实短信 |
| 主壳 / 引导 | `App.tsx` + `checkOnboardingStatus` | `supabase.auth.getUser()` 无用户 → `clearOnboardingState`、`setShowOnboarding(false)` | `user_profiles` 查不到或超时 → 走缓存 / Context / **2s 超时分支**（逻辑复杂，见 §4） | 多路竞态：Context、内存缓存 10s、5min、`profileRef` |
| 档案与设置 | `UserProfileContext` + `ProfileSettingsScreen` 等 | Query `enabled: !!user?.id` | `getProfile` 返回 `null` → Context 内有「无档案」处理分支 | `userProfileService.updateProfile` 可对**无行用户 insert** |
| 健康卡片（体重等） | `useWeightRecordsQuery` 等 | `enabled: !!user?.id` → 空列表，不请求 | 无记录 → 空列表 UI | RLS 拒绝时表现为 **error**，需组件层 `isError` 提示 |
| Node 认证 API | `POST /api/auth/*`（`server/index.js` 挂载） | 返回 401/400 | — | **C 端主路径不经过此处**；与 C 端 Supabase 直连 **双轨**，易口径漂移 |

**核查结论**：未登录入口统一依赖 **Supabase session**；**无统一「权限不足」错误码**，多为空态或 `Error` 字符串。引导入口 **强依赖** `App.tsx` 与 `user_profiles.has_seen_onboarding`，分支多，属 **P0 回归重点**。

## 2. 状态矩阵（核心状态与允许流转）

### 2.1 认证会话（C 端）

| 状态 | 含义 | 典型下一状态 |
|------|------|----------------|
| 无会话 | `user === null` | `signInWithPhone` 成功 → 有会话 |
| 有会话 | `user` + `session` 有值 | `signOut` → 无会话；`TOKEN_REFRESHED` 仍为有会话 |
| 测试模式 | `isTestMode()` 假用户 | 本地 `setTestAuthState`，不经 Supabase |

**退出**：`signOut` 清 `sb-*`、`_user_signout_flag`、`clearAllUserStorage` 等（`AuthContext.tsx`）。

### 2.2 引导（Onboarding）

| 维度 | 来源 | 说明 |
|------|------|------|
| UI 是否展示引导 | `App.tsx` `showOnboarding` | 与 `has_seen_onboarding`、`onboardingJustCompleted`、`showOnboarding` 互锁 |
| 草稿数据 | `OnboardingContext` + `userStorage`（`onboarding_data` / `onboarding_step` 等） | 用户隔离键 `*:user:{userId}` |
| DB 真相 | `user_profiles.has_seen_onboarding`、`onboarding_completed` | `userProfileService` 映射字段 |

**允许流转（设计意图）**：新用户 `has_seen_onboarding = false` → 完成引导或显式保存 → `true`；**禁止**依赖已删除的「登录后 bulk sync localStorage → DB」路径（`AuthContext` 顶部注释）。

### 2.3 健康记录（以体重为例）

| 状态 | Query | Mutation |
|------|-------|----------|
| 空闲 | `useQuery` success | — |
| 加载 | `isLoading` | `isPending`（add/update/delete） |
| 失败 | `isError` + Supabase `error` | 抛错至 `mutateAsync` 调用方 |

**无显式「业务状态机」**：同一天多条 `weight` 记录由 **DB 行数** 体现，未见「当日唯一」约束（若需产品规则要加 DB 唯一或应用层校验）。

## 3. 主流程（正常链路 · 逐步）

### 3.1 登录 / 注册合一（C 端）

1. 用户打开 `LoginPage`，输入手机号、勾选协议。  
2. **「获取验证码」**：`handleSendCode` **仅** `setTimeout(1s)` + `console.log`，**未调用** `/api/auth/send-verification-code` 或短信服务。  
3. 用户输入 **6 位数字**，点登录 → `signInWithPhone(phone, code)`。  
4. `AuthContext`：`email = phone + @healthapp.local`，`password = code` → `signInWithPassword`。  
5. 若 `Invalid login credentials`：先查 `user_profiles.phone`；**若已有用户** → 直接返回「验证码无效或已过期」（**实际为密码错误**）；**若无** → `signUp` + `user_profiles.insert`（`has_seen_onboarding: false`，最多重试 3 次）。  
6. 成功 → `setUser` / `setSession`，清 `_user_signout_flag`。  
7. `App` 侧 `checkOnboardingStatus` 根据 DB / Context / 缓存决定 `showOnboarding`。

### 3.2 档案加载与更新

1. `useUserProfileQuery`：`queryKey ['user-profile', user.id]`，`staleTime` 10 分钟。  
2. `userProfileService.getProfile` → `user_profiles` 单行 `maybeSingle()`。  
3. `updateProfile`：有则 `update`，无则 `insert`（upsert 语义）。

### 3.3 健康记录（体重）

1. `useWeightRecordsQuery`：`weightService.getRecords` → `health_records` 且 `record_type = 'weight'`。  
2. 新增：`insert` 一行，`onSuccess` → `invalidateQueries(['weight-records', userId])` + `dashboard-data` 当日 key。

## 4. 异常流程（失败、超时、重复提交、乱序）

| 场景 | 代码行为 | 问题等级 |
|------|----------|----------|
| Supabase 不可达 | `signInWithPhone` 捕获 `Failed to fetch` 等 → 返回中文 `Error` | P0 提示可用 |
| 手机号 API 登录整段超时 | **`SIGN_IN_WITH_PHONE_TOTAL_MS`（45s）** 内完成 `getSession` 检查、`fetch(login-with-code)`、`setSession`；逾界返回超时错误 | —（与 v1.8 一致） |
| `LoginPage` 超时 | **已收敛（v1.8）**：不再单独定时；**`signInWithPhone`** 用统一 **`SIGN_IN_WITH_PHONE_TOTAL_MS`（45s）** 截止 `fetch` + **`setSession`**，避免双计时器 | — |
| 注册后 `user_profiles` 连续失败 | 3 次重试后 `signOut`，返回「无法创建用户档案」 | P0 |
| `user_profiles` 并发插入 `23505` | 尝试改 `signInWithPassword` 补救 | P1：依赖竞态形态 |
| 引导 DB 查询超时 | `App.tsx` **6s** `Promise.race`；失败走缓存 / `profileRef`；已移除 **setInterval + 陈旧 isLoading** 分支 | **P0**：弱网仍依赖缓存与后续 profile effect，建议 E2E |
| 重复点击「保存体重」 | `mutateAsync` **无**客户端幂等键；可产生 **多条同日记录** | P1（视产品是否允许） |
| 回调乱序 | 健康记录 **无**「支付回调」类乱序；Auth 以 `onAuthStateChange` 为准 | — |
| Node `/api/auth/login-with-code` | **已改为真实 OTP 校验（v1.11）**：验证码需命中服务端缓存且未过期；新增 **60s 发送节流**、**5 次校验上限** | —（仍建议评审对外暴露策略） |

## 5. 数据口径（主表、快照、SoT）

| 数据域 | SoT（权威源） | 本地/缓存 | 说明 |
|--------|----------------|-----------|------|
| 登录身份 | `auth.users`（Supabase） | `sb-*` session、`AuthContext` state | C 端直连 |
| 档案展示字段 | `user_profiles` | React Query `['user-profile', id]`；`userStorage` 仅引导草稿等 | `updateProfile` 写回 DB |
| 引导完成标记 | **`user_profiles.has_seen_onboarding`（DB）** | `onboardingStatusCacheRef`（10s）、5min 缓存 | **以 DB 为最终真相**；缓存仅为减闪屏 |
| 体重/饮水/步数等 | **`health_records`**，按 **`record_type`** 区分 | RQ 列表缓存 5min | 无独立「快照表」；列表即事实 |
| 仪表盘聚合 | `dashboardDataService` 等读 `health_records` + 配置 | 各 `['dashboard-data', …]` | 与写入一致性依赖 **invalidate** |

**非 SoT**：`LoginPage` 的「验证码已发送」**不**代表后端已发码。

## 6. 前后端契约（输入/输出、错误码、用户提示）

### 6.1 C 端 ↔ Supabase（主路径）

- **非 REST 自研契约**：使用 Supabase JS，`error.code` / `error.message`（PostgREST/Auth）。  
- **用户可见文案**：多在 `LoginPage` 对 `signInError.message` 做 **字符串 includes** 分支（`注册失败`、`Supabase` 等），**非稳定错误码枚举**。  
- **档案/健康**：组件若未统一 `try/catch`，可能仅 `console.error`。

### 6.2 Node `/api/auth`（次要路径）

| 接口 | 请求 | 响应 | 备注 |
|------|------|------|------|
| `POST /send-verification-code` | `{ phone }` | `message` + **mockCode（生产不应返回）** | 短信 TODO |
| `POST /login-with-code` | `{ phone, verificationCode }` | `user` + `session` 或 `error` 字符串 | 与 C 端逻辑平行 |
| `POST /reset-password-by-phone` | `{ phone, newPassword }` | 403 除非 `ALLOW_INSECURE_PHONE_PASSWORD_RESET=true` | 管理/救急用 |

**缺口**：无统一 **`{ code, message }`** 规范；C 端主流程 **未绑定** 上述 API。

## 7. 一致性策略（缓存、并发、幂等）

| 机制 | 实现 | 缺口 |
|------|------|------|
| 档案缓存 | RQ `staleTime` 10min；`update` 后 `setQueryData` + `invalidate` | 多 Tab 不同步需 `refetchOnWindowFocus` 策略再评估 |
| 健康记录缓存 | `invalidateQueries` 按 `userId` | 范围 key 与 `startDate/endDate` 变体可能留下 **陈旧切片**（需全量 invalidate 或 predicate） |
| 用户切换 | `clearPreviousUserData` / `signOut` 清 `*:user:{id}` | 依赖调用顺序正确 |
| 幂等 | **无**请求 ID；`health_records` insert **无**去重 | 双点提交 → 双行 |
| 并发写档案 | `update` 按 `user_id` **最后写赢** | 无版本列乐观锁 |

### 8.2 建议巡检 SQL（只读示例，按环境替换 `:user_id`）

```sql
-- 某用户近 7 天各类型健康记录条数
SELECT record_type, COUNT(*) AS n
FROM health_records
WHERE user_id = :user_id
  AND recorded_at >= NOW() - INTERVAL '7 days'
GROUP BY record_type
ORDER BY n DESC;

-- 档案与引导标记
SELECT user_id, phone, nickname, has_seen_onboarding, onboarding_completed, updated_at
FROM user_profiles
WHERE user_id = :user_id;

-- 同日多条体重（若产品期望单日一条）
SELECT user_id, (recorded_at AT TIME ZONE 'Asia/Shanghai')::date AS d, COUNT(*) AS n
FROM health_records
WHERE record_type = 'weight'
GROUP BY user_id, d
HAVING COUNT(*) > 1
ORDER BY n DESC
LIMIT 50;
```

## 9. 验收清单（最小回归包 · 10 条）

1. 新手机号：请求验证码后输入**正确 OTP** 首次登录 → **注册成功**，`user_profiles` 存在且 `has_seen_onboarding = false`（或等价）。  
2. 同手机号第二次：输入 **不同** 6 位 → 应提示 **验证码无效或已过期**（密码错误），**不**新建第二账号。  
3. 登录成功后 **45s 内** 无「假超时」误报（超时仅由 `signInWithPhone` 统一控制）。  
4. 退出登录后：**无**上一用户 `userStorage` 键残留；再登另一账号 **不串数据**。  
5. 引导完成后再进 App：**不**反复进入引导（`has_seen_onboarding` 与 `App` 缓存一致）。  
6. **断网 / Supabase 慢**：引导检查 **6s** `Promise.race` 超时后 **不**长期白屏；有明确降级或重试（记录当前行为作基线）。  
7. 体重保存一条 → 列表与 Dashboard **当日**数据 **无需手动刷新** 即更新。  
8. `user_profiles` 无行时，设置页保存 → **自动 insert** 成功。  
9. RLS：用 **B 用户 token** 请求 **A 用户** `user_id` 的 `health_records` → **拒绝**（需在 Supabase 策略已启用前提下验证）。  
10. `POST /api/auth/login-with-code`（若对外）：确认 **错误 OTP 会拒绝**，且 60s 发送节流 / 5 次失败上限生效。

### 14.7 OTP Redis 强制策略（生产）与排查清单（v1.13）

> 适用范围：`server/services/otpStore.js` + `server/index.js` 启动路径。  
> 目标：避免生产环境 OTP 回退到进程内存，降低多实例下验码不一致与安全暴露风险。

#### 策略定义（与代码一致）

- 生产环境（`NODE_ENV=production`）必须使用 `OTP_STORE_PROVIDER=redis`。  
- 生产环境下 Redis 视为 **必需依赖**：不可连、未配置 URL、认证失败等场景均 **禁止自动降级内存**。  
- 服务在启动时先执行 OTP 存储就绪检查（`ensureOtpStoreReady()`）；检查失败则 `process.exit(1)`，服务不对外提供接口。  
- 非生产环境可继续使用 `auto`（允许降级）以降低本地开发门槛。

#### 部署环境变量基线（生产）

| 变量 | 要求 | 说明 |
|------|------|------|
| `NODE_ENV` | `production` | 触发强制策略 |
| `OTP_STORE_PROVIDER` | `redis` | 生产必须显式设置 |
| `REDIS_URL`（或 `OTP_REDIS_URL`） | 必填 | Redis 连接串；建议统一使用 `REDIS_URL` |
| `OTP_REDIS_PREFIX` | 可选 | OTP key 前缀，默认 `otp:phone:` |

#### 启动失败排查 checklist

1. 确认 `OTP_STORE_PROVIDER` 在生产是否为 `redis`（避免误配 `auto` / `memory`）。  
2. 确认 `REDIS_URL`（或 `OTP_REDIS_URL`）存在，且未被错误覆盖为空值。  
3. 从服务所在网络验证 Redis 可达（DNS、端口、安全组、VPC）。  
4. 验证 Redis 凭据与 ACL 权限（至少具备 `GET/SET/DEL/EXPIRE` 相关能力）。  
5. 查看启动日志关键字：`Failed to start server`、`OTP_STORE_PROVIDER=redis`、`Redis`。  
6. 若多环境共用模板，检查生产变量注入顺序，防止被默认 `.env` 回退覆盖。  

#### 运行期验收建议

- 冷启动时验证：服务仅在 Redis 就绪后开始监听端口。  
- 故障演练：人为断开 Redis 后重启服务，应启动失败而非进入内存 fallback。  
- 灰度观察：确认 `/api/auth/send-verification-code` 与 `/api/auth/login-with-code` 在多实例场景下一致命中 OTP。  

### 14.8 认证面继续收口（v1.14）

> 适用范围：`server/routes/auth.js`、`server/services/smsService.js`、`src/config/supabase.ts`、`src/contexts/AuthContext.tsx`、`src/components/LoginPage.tsx`。  
> 目标：默认关闭高风险入口、提升可审计性、让生产配置错误尽早失败。

#### A. `reset-password-by-phone` 默认关闭 + 审计

- 默认关闭：仅当 `ENABLE_PHONE_PASSWORD_RESET=true` 才允许调用。  
- 可选二次鉴权：若配置 `PHONE_PASSWORD_RESET_TOKEN`，请求必须携带 `x-admin-reset-token`。  
- 全链路审计：关闭拦截、鉴权失败、参数失败、用户不存在、更新失败、成功、异常都记录结构化日志。  
- 审计字段：`requestId`、`ip`、`actor`（`x-admin-user`）、手机号脱敏、错误原因。

#### B. 短信通道接入位（Webhook 适配）

- `send-verification-code` 已通过 `smsService` 发送，不再只打 placeholder 日志。  
- `SMS_PROVIDER=webhook` 时调用 `SMS_WEBHOOK_URL`；失败返回 `SMS_SEND_FAILED` 并清理 OTP。  
- 生产环境若仍配置 `SMS_PROVIDER=mock`，会被视为发送失败（防止“假发码”误上生产）。

#### C. 前端 Supabase 生产 fail-fast

- 生产环境若 `VITE_SUPABASE_URL` 或 `VITE_SUPABASE_ANON_KEY` 缺失/非法，启动阶段直接抛错中止。  
- 非生产环境仍允许占位配置，便于本地调试。

#### D. 登录错误契约收敛

- `AuthContext.signInWithPhone` 将后端 `payload.code` 透传为结构化错误码。  
- `LoginPage` 按 `code` 优先分支（如 `OTP_IP_RATE_LIMIT`、`INVALID_VERIFICATION_CODE`、`LOGIN_TIMEOUT`），减少对字符串 `includes` 的依赖。  
- 保留 message 兜底，兼容旧路径与未知错误。
