# 业务总图 + 验收清单

> 本文档将「用户配送执行」「餐食/补剂展示与配置约束」「订单支付与开启服务」「商品/费率/订单管理」四条链路组合为一条可交付闭环，并给出数据流、规则口径与发布前验收清单。  
> **不包含**：真实三方支付验签、三方物流、地图/选址等外部集成（实现未接时按已知缺口处理，不改变内部契约）。

- **订单生命周期与状态字段**（创建 → 支付 → 确认预留 → 开启服务 → 结束 → 评论预留、管理/C 端展示对齐、`promoteOrderToProcessing` 同时更新项等）：见同目录 **`order-flow-and-status.md` 全文**；销售人员细则见其 **第三节**。

## 2. 四条链路定义（在总闭环中的位置）

| 代号 | 链路名称 | 核心职责 |
|------|----------|----------|
| **L1** | 用户配送执行 | 日期、餐次、地址、配送计划落库、锁窗与编辑回写 |
| **L2** | 餐食/补剂展示与配置约束 | 订单契约餐次与 UI 展示一致；补剂摘要口径；禁止扩餐 |
| **L3** | 订单支付与开启服务 | 支付幂等/防回退、状态推进；开启服务后 `order_status=processing` 与 `delivery_state` / `start_time` 等与 **`order-flow-and-status.md`** 一致 |
| **L4** | 商品 / 费率 / 订单管理（B 端） | 可售配置、结算版本、引用保护；**代用户建单**（含销售人员归属）、运营侧订单操作口径 |
| **L5** | 用户与健康数据 | 注册/登录/退出、引导与档案、设置；体重/饮水等 **`health_records`** 卡片的数据结构与交互；本地隔离与 RLS；**不含订单履约**（见 **`L5-用户与健康数据治理-v1.0.md`**） |

## 3. 组合后的完整业务流（用户主路径）

1. **线下成交与建单**：线下销售与用户达成成交意愿后，由**管理后台创建订单**；建单时**须选择关联销售人员（业务必填）**，`salesperson_id` 写入 `orders`（后续可扩展为销售人员自主建单）。可与推荐人自动带出/预选并存，提交前须确认为有效 ID；空值与展示排查见 **`order-flow-and-status.md` 第三节**。**不存在** C 端用户自行选品、自助下单的默认主路径；订单一经创建即为「已生成订单」，通常 **`payment_status` 待支付**（其余以库内枚举为准）。
2. **支付**：由 **C 端用户支付** 或 **管理后台代录支付**（见 `order-flow-and-status.md` 第四节）；支付相关接口**不修改** `salesperson_id`。订单进入已支付态后，`order_status` 等按状态机进入可开启服务的前置状态；**销售/财务确认**若启用，以 `confirm_status` / `confirm_time` 等字段为准（管理后台预留，细节见 **`order-flow-and-status.md` 第一节**）。
3. **订单快照（关键）**：与交付强相关的餐次写入 **`orders.included_meal_types`**（中文快照），避免后续商品疗程变更污染历史订单语义。
4. **开启服务前配置（L1 + L2）**  
   - 选择配送日期 / 排除日。  
   - **餐次严格跟单**：仅允许订单契约内餐次，不允许用户额外增加订单外餐次。  
   - 配置地址：默认餐次与地址映射须**覆盖订单内全部餐次**；任一餐次缺地址则**禁止生成/确认配送计划**。  
   - 生成并确认配送计划：写入 **`delivery_schedules`**（`delivery_type = meal`），并绑定 **`order_id`**（主流程及关键旁路需一致）。
5. **开启服务（L3）**（C 端用户完成配送计划配置后触发）  
   - 必须已支付。  
   - 若订单存在餐食餐次契约（快照非空）：须已存在与该订单关联的 meal 排期，否则拒绝进入服务中。  
   - 成功后 **`order_status` → `processing`**，并同步 **`delivery_state` → `started`**、**`start_time`** 等（与 `promoteOrderToProcessing` / **`order-flow-and-status.md` 第二节、第五节** 一致），保证管理端与 C 端「已开启 / 服务中」展示一致。
6. **履约与运营（L4）**：后台查看订单、商品、费率版本；对已引用商品删除拦截；结构变更按「在途交付锁定」规则处理。
7. **服务结束 / 评论（预留）**：周期结束、评价等字段与入口以 **`order-flow-and-status.md`** 及库表为准。
8. **退单与删除（订单治理）**：已支付订单**退单**、未支付订单**删除**的条件与字段效果（如 `refund_*`、`payment_status`、`order_status`、业绩统计排除规则）见 **`order-flow-and-status.md` 第六节**；与支付回调、状态机冲突时以治理文档与接口守卫为准。

## 4. 主流程分支（异常 / 边界）

| 场景 | 行为 |
|------|------|
| 重复支付 / 重复回调 | 幂等：不重复推进；返回约定错误码 |
| 并发支付写入 | 条件更新：仅 `pending` 可首笔成功推进 |
| 回调与订单当前态冲突 | 条件更新失败 → 状态冲突类错误；事件表记录结果便于排障 |
| 多笔已支付订单、无明确 `order_id` | 不自动串单推进服务；须从订单入口带单 |
| 仅部分餐次有默认地址 | 生成配送计划前硬拦截，提示缺失餐次 |
| 锁窗内 / 已过配送开始时刻的当日餐次 | 不参与可编辑集合或按地址治理规则跳过回写 |
| 纯补剂订单 | 用户订单展示不出现虚构「健康餐包」块 |
| 删除已被订单引用的商品 | HTTP 409 + `PRODUCT_REFERENCED_BY_ORDERS`；列表可禁用删除按钮 |
| 订单主体数据创建后不可改 | 除**退单**、**内部备注**（如 `notes`）等明确允许项外，金额、商品、`salesperson_id` 等均不可改；见 **`order-flow-and-status.md` 第六节** |
| 未支付订单删除 / 已支付退单 | 仅未支付等态可删单；已支付须走退单及业绩排除规则；见 **`order-flow-and-status.md` 第六节** |

## 5. 数据流总图（SoT、快照、派生）

### 5.1 分层原则

- **交易 SoT**：`orders`（`payment_status`、订单态、服务态；**`salesperson_id` 建单写入**；`confirm_*` 等确认字段若启用见 **`order-flow-and-status.md`**）。
- **商品 SoT**：`products` + 关联 `meal_plans` / `supplement_plans`（**当前可售配置**）。
- **执行 SoT**：`delivery_schedules`（用户端履约视图与后台排期依据）。
- **快照**：`orders.included_meal_types` — **历史订单餐次契约**，配置与展示优先读快照。

### 5.2 典型读写方向（简图）

```
商品配置 (products → meal_plans)
        ↓ 管理后台建单（含 salesperson_id、商品等）/ 触发器或写入逻辑
orders（payment_status、included_meal_types 快照 …）
        ↓ 驱动
日期/餐次/地址配置 (C 端状态 + 订单契约)
        ↓ 校验通过后写入
delivery_schedules (order_id, meal_type, address, lock …)
        ↓ 满足条件
POST start-service / promoteOrderToProcessing
        → order_status=processing，delivery_state=started，start_time …
```

### 5.3 已移除的历史路径（勿再引用）

- **旧版 `POST /api/delivery-schedules/sync`**：已从 Node 路由**删除**。配送计划写入以 **App 内 `deliveryScheduleService.syncUserDeliverySchedules` 直连 Supabase `delivery_schedules`** 与既有 **`GET /api/delivery-schedules`** 等为准；误配旧路径将得到 **404**。

## 6. 规则汇总（硬规则优先）

### 6.1 L2 餐食 / 补剂

- **硬**：配置链路餐次 ⊆ 订单快照餐次；不得扩餐。  
- **硬**：缺任一契约餐次地址 → 不允许生成/确认配送计划。  
- **展示**：补剂侧统一「个性化补剂方案 + 份数/天数」摘要，避免慢查询拉明细。  
- **管理端订单详情餐食展示**：以 **`orders.included_meal_types`** 为主；份数按 `duration × 餐次数` 与快照餐次一致。

### 6.2 L1 地址与配送

- 默认餐次排他、锁窗、当日已过配送开始则不当作可编辑履约项（与 `address-crud-governance` 一致）。  
- 地址编辑后对 `delivery_schedules` 快照字段回写：仅未来可改行；锁窗内跳过。

### 6.3 L3 支付与服务

- **订单来源**：订单由管理后台预先创建；C 端仅支付与履约配置，**不**在支付环节写入或修改 `salesperson_id`（与 **`order-flow-and-status.md` 第三节、第四节** 一致）。  
- 用户确认支付：须登录且订单归属本人；非 `pending` 返回已支付类冲突码。  
- 回调：`payment_event_id` 幂等；状态转移由 `evaluatePaymentTransition` 守卫；订单 `update` 带 **`payment_status` 条件** 降低并发覆盖。  
- **支付确认**：仅 **Node** `POST /api/orders/:id/confirm-payment`；本仓库 **Supabase Edge Functions 目录下无** `confirm-payment`。  
- `start-service`：已支付 + 有餐次契约则须有 meal 排期；`promoteOrderToProcessing` **仅走后端 API**，禁止前端直连改订单绕过规则；成功后 **`order_status`、`delivery_state`、`start_time`** 等与 **`order-flow-and-status.md` 第二节、第五节** 一致。  
- 配送计划保存成功但服务未推进：成功文案须区分「计划已保存」与「已进入服务中」。

### 6.4 L4 商品 / 费率 / 管理订单

- **建单**：须写入有效 **`salesperson_id`（业务必填）**；详见 **`order-flow-and-status.md` 第三节、第四节**。  
- **创建后不可改**：订单生成后，除退单、内部备注等允许项外，主体字段不可改（与 **`order-flow-and-status.md` 第六节** 一致）。  
- 删除商品：若 `orders` 中存在 `product_id` 引用 → **409** `PRODUCT_REFERENCED_BY_ORDERS`；列表可用 `has_order_references` 禁用删除。  
- 管理端 `PATCH .../start`、`.../end`：须与状态机及服务前置校验一致，并写审计。  
- 费率：以 DB 为 SoT，版本发布与结算选版见 `product-config-governance`。

## 7. 验收清单（发布最小集）

### 7.1 端到端（必测）

1. 管理后台创建订单（含选择销售人员等必填项）并完成支付后，`orders.included_meal_types` 与商品疗程餐次一致（或符合触发器/回填规则）。  
2. 开启服务流程中，日期页**无法**勾选订单外餐次。  
3. 仅部分餐次配置默认地址时，生成配送计划**被拦截**，文案列出缺失餐次。  
4. 全餐次有地址后，可生成计划；`delivery_schedules` 存在对应 `order_id` 的 meal 行。  
5. 调用 `start-service` 后订单进入 `processing`；未支付调用返回 `ORDER_NOT_PAID`。  
6. 有餐次契约但无 meal 排期时，`start-service` 返回 `ORDER_NO_DELIVERY_PLAN`。  
7. 配送计划保存成功但服务推进失败时，提示**不**误称「订单已进入服务中」。  
8. 纯补剂订单在用户订单列表**不**出现虚构餐食包卡片。  
9. 已被订单引用的商品删除：接口 409 + 前端删除按钮禁用（或明确错误提示）。  
10. 全仓库无对 **`POST /api/delivery-schedules/sync`** 的调用；该路由已删除（误配则 404）。

### 7.2 L3 支付与回调（建议）

11. 同一订单重复确认支付：符合 `PAYMENT_ALREADY_CONFIRMED` 或并发冲突码口径。  
12. 同一 `payment_event_id` 重复回调：幂等成功，不重复改单。  
13. 非法状态转移回调：返回冲突类错误，事件表可追溯。

### 7.3 L1 地址（建议）

14. 锁窗内编辑地址：按规则拦截或跳过不可改行。  
15. 已过当日配送开始时间的餐次：不出现错误锁窗提示。

### 7.4 L4 管理端（建议）

16. 订单详情侧栏「订单状态」与 `order_status` 枚举展示一致（非仅「已创建/已取消」）。  
17. 管理端开启/结束服务与 C 端规则一致，无裸改字段旁路。  
18. 管理后台新建订单：**未选有效销售人员则不应提交成功**（与业务必填口径一致；若 DB 仍允许 null，以产品验收为准推动前后端收口）。  
19. 支付完成后：`salesperson_id` 与建单时一致，不因 `confirm-payment` / 回调被清空或改写。  
20. 退单、未支付删除订单后的字段与列表表现与 **`order-flow-and-status.md` 第六节** 一致（含已支付不可删、退单后业绩排除等）。
