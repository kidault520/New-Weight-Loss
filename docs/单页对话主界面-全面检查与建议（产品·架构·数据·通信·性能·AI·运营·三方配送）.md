# 单页对话主界面改造 — 全面检查与建议（务实版）

> **目标规模**：最大用户量约 10 万，日订单量最大约 100 单；涉及与三方运力（配送）打通。  
> **原则**：只做当前规模与阶段**必要**的项，避免过度设计和理想化；先跑通、再按需迭代。

本文档在「单页对话主界面-旧结构到新结构映射表」基础上做**补充检查**，标出可能遗漏或现有 app 存在问题的点，并给出**可执行、可分期**的建议。**不替代**映射表，与之配合使用。

> **口径勘误（与当前实现对齐）**  
> - 餐食配送执行主表：**`delivery_schedules`**（`delivery_type = meal`）。下文表格中若出现历史表名 **`meal_delivery_schedules`**，应以 **`delivery_schedules`** 为准。  
> - 配送写入：App 内 **`deliveryScheduleService.syncUserDeliverySchedules`** 直连 Supabase；**无** `POST /api/delivery-schedules/sync`。  
> - 支付确认：**Node** `POST /api/orders/:id/confirm-payment`（非 Supabase Edge）。

## 一、数据结构与存储

### 1.1 已覆盖与待确认

| 项 | 状态 | 说明与建议 |
|----|------|------------|
| 每天一结、按日拉取对话 | 映射表已约定 | 需在 service 层提供 `getMessagesByDay(userId, date)`，按用户时区 0:00–24:00 查询；`chat_messages` 已有 `created_at`，无需新字段。 |
| 每日聊天标记（左侧抽屉列表） | 映射表二十二已写 | **优先方案 A**：用当日首条消息截断，无新表、改造成本低；方案 B 新表可等有明确需求再上。 |
| 业务卡片持久化（配送/血糖/报告卡） | 映射表二十二已写 | 扩展 `message_type` + 通用 jsonb 或复用 `quick_entry_data` 结构即可，无需必选新表。 |
| 配送计划与配送记录 | **`delivery_schedules`**（主表） | 用户端展示、改地址/锁单等均以此表为准，并与 `order_id` 关联；**三方运力**若写入配送状态，需预留或新增字段（见第八节）。 |

### 1.2 现有 app 可能存在的问题

| 问题 | 建议 |
|------|------|
| 餐食计划配置与配送计划多源 | `meal_plan_config_data` 在 user_profiles（JSONB），配送明细在 **`delivery_schedules`**；部分状态在 localStorage（如 mealAddresses）。**改地址/改时间**的落库与 UI 须与 `delivery_schedules` 一致，避免前后端不一致。 |
| 健康数据多表与 health_records | 部分能力用 health_records 统一表，部分用独立表（如 exercise_records）；查询与索引要按「按用户+按日」高频路径优化，避免 N+1 或全表扫描。 |
| 时区 | 按日与截止时间若用 UTC 会错位。**务实做法**：先按浏览器本地时区或固定「中国时区」算当日与截止时间；若后续有海外用户再加 profile 时区字段。 |

### 1.3 规模粗算（10 万用户、100 单/日）

| 数据 | 量级 | 建议 |
|------|------|------|
| chat_messages | 按日存，约 10 万 × 30 条/月 ≈ 300 万条/月 | 按 (user_id, created_at) 分页查询即可；索引已有，**不必先做分区表**，等真遇到慢再考虑。 |
| 配送相关 | 100 单/日 × 2–3 餐 ≈ 200–300 条/日 | 单表足够；有 `(user_id, delivery_date)` 等常用查询索引即可。 |
| 健康记录 | 取决于录入频率 | 沿用现有表与索引；新查询按「用户+日期」加索引即可。 |

## 二、App 架构与改造一致性

### 2.1 与架构规范的契合

- **直连 Supabase、React Query、无多余抽象**：改造后仍应保持「组件 → Hook → Service → Supabase」，不因单页+对话而新增一层「对话编排服务」除非确有 10 倍收益。
- **单页主界面**：入口收敛后，**状态机要简单**：当前选中的「日期」、当前打开的「抽屉」、置顶卡数据来源（今日/执行计划/配送），避免分散在多个 Context 或全局状态里重复。

### 2.2 现有 app 可能存在的问题

| 问题 | 建议 |
|------|------|
| App.tsx 体积过大 | 映射表已把路由/模态拆到 AppRouter、useAppModals；改造后继续控制 App 只做「壳+状态分发」，业务逻辑留在页面级与 Hook。 |
| 多处 localStorage 与 DB 双写 | 如 mealAddresses、dashboard 顺序等；改造时**明确哪些以 DB 为准、哪些仅本地**，避免改地址后刷新丢失或与后端不一致。 |
| 执行任务与通知类型 | `daily_execution_tasks` 的 `notification_type` 等已较多；新「今日待办」与对话任务卡若沿用该表，需对齐类型与去重逻辑，避免重复或漏展示。 |

## 三、信息通信（API、实时、推送、离线）

### 3.1 已具备

- **Supabase Realtime**：chat_messages 的 UPDATE/DELETE 已订阅，用于 quickEntry 确认等；**按日加载**后，需确保订阅的 filter 或前端只处理「当前选中日」的消息，避免跨日干扰。
- **React Query**：staleTime、invalidate 已用；改造后「今日」「选中日」的 key 要区分（如 `['chat', userId, dateKey]`），避免缓存串日。

### 3.2 需补充或明确

| 项 | 建议 |
|------|------|
| 推送（配送提醒、血糖提醒） | **先做应用内提醒**（置顶卡倒计时、到点提示）即可上线；Push 通知可二期再做（需设备 token、权限、后端或 Supabase 配置）。 |
| 离线与弱网 | 对话区读缓存、提交时提示「请连接网络」即可；改地址/改时间**防重复提交**（如提交中禁用按钮、或简单 request_id），不必先上完整幂等与回滚。 |
| AI 对话 API | 外部 AI 需**超时**（如 15s）与**失败提示**；限流可按「每用户每日条数」简单控制，避免成本暴增，不必先做复杂排队。 |
| 安全与鉴权 | 新增按日查询、每日摘要等仍走 Supabase RLS，只查当前 user_id；不新增裸接口。 |

## 四、代码加载效率与性能

### 4.1 已具备

- React.lazy + LazyComponents、Suspense；React Query 缓存。
- 映射表要求：置顶卡 + 对话首屏优先，抽屉按需加载。

### 4.2 建议

| 项 | 建议 |
|------|------|
| 单页主包体积 | 保持**抽屉/次级页懒加载**（现有 LazyComponents 延续），主包只含主界面+置顶卡+今日对话即可。 |
| 长列表 | 左侧抽屉「对话记录」先**分页或限制条数**（如最近 90 天）；若后续卡顿再考虑虚拟滚动。 |
| 图片与静态资源 | 现有方式沿用即可；若单张图过大再考虑压缩或缩略图，不必先上 CDN。 |

## 五、AI 能力与边界

### 5.1 当前与改造后

- 对话内：健康指标识别（healthMetricDetectionService）、快捷卡片、AI 回复；改造后仍以「对话 + 结构化卡片」为主，AI 用于回复、摘要、建议。

### 5.2 需明确与建议

| 项 | 建议 |
|------|------|
| AI 负责范围 | 文案上**仅辅助、不替代专业判断**，符合健康类上架即可；不在应用内宣称疗效。 |
| 敏感数据 | 若健康数据经第三方 AI：选型时看对方隐私条款（是否用于训练）；可只传必要字段或摘要，不必先做完整脱敏体系。 |
| 成本与限流 | 按「每用户每日对话条数」做简单上限（如 N 条）并提示，控制成本即可。 |
| 报告/周报生成 | 若生成较慢：前端**超时提示**（如「生成中，请稍后到周报查看」），不必先做完整异步队列与 Realtime 推送。 |

## 六、开发、上架与合规

### 6.1 上架相关

| 项 | 建议 |
|------|------|
| 隐私政策与用户协议 | 登录页已有入口；单页改造不改变入口，确保**隐私政策**中说明：健康数据、对话记录、配送地址的收集与使用范围；若接 CGM/设备，需说明数据共享与存储方式。 |
| 健康类应用声明 | 应用商店对健康/医疗相关有要求；需明确「健康管理/减脂指导」定位，不宣称疗效，避免被归类为医疗设备或医疗建议。 |
| 权限 | 通知、相机（若有拍照上传）、蓝牙（若 CGM 直连）等，需在合适时机申请并在应用内说明用途。 |

### 6.2 开发与协作

| 项 | 建议 |
|------|------|
| 环境与配置 | 敏感配置用 `.env`，不写死；开发/生产可区分即可。 |
| 错误与监控 | 有资源可接简单错误上报（如 Sentry）和少量关键埋点（如配送确认、打卡）；**无则先靠用户反馈与控制台**，不 blocking 上线。 |
| 版本与兼容 | 新表/新字段用迁移脚本；尽量向后兼容（旧端可忽略新字段），避免强制清缓存。 |

## 八、三方运力（配送）打通

### 8.1 当前状态

- 代码中**未发现**与第三方配送 API（如达达、蜂鸟、美团跑腿等）的直接对接；配送计划与状态来自自有表 **`delivery_schedules`**。

### 8.2 若接入三方运力，建议（接的时候再细做）

| 项 | 建议 |
|------|------|
| 谁对接 | **后端**调三方 API，前端只调自家接口（创建/改地址改时间/查状态）；三方 key 不放前端。 |
| 表与规则 | 配送表预留**第三方订单号、运力状态**；「送餐前 1h 可改」取我方与三方**更严**的一边，避免用户能改但三方已锁单。 |
| 状态同步 | 若三方有回调，后端接回调更新状态，前端轮询或 Realtime 展示即可；日 100 单量级压力很小，人工兜底异常单即可。 |

## 十、务实优先级（可勾选落地）

只做当前阶段**必要**的，其余按需迭代。

| 优先级 | 内容 | 说明 |
|--------|------|------|
| **P0 必做** | 改地址/改时间唯一落库、按日查对话、置顶卡与选中日关系、Realtime 按日过滤 | 不做会导致数据错乱或体验割裂。 |
| **P0 必做** | 时区（先固定或浏览器）、防重复提交、AI 超时与简单限流 | 上线前要稳。 |
| **P1 上线前尽量** | 应用内提醒（送餐前/餐后）、隐私政策与健康类表述、.env 配置 | 影响合规与体验，尽量有。 |
| **P2 有余力再做** | Push 通知、每日摘要新表、错误上报与埋点、推送时间配置化、三方运力对接 | 不 blocking 首版，可二期。 |

## 十一、与映射表的衔接

- **实施前检查清单**（映射表十九）：与本文档 **P0** 对齐，先保证「数据一致、按日正确、不重复提交、AI 不崩」。
- **Phase 1**：单页+左侧抽屉+每天一结 + **按日查询、时区、置顶卡与选中日**；其余能懒加载就懒加载。
- **Phase 2 及以后**：配送规则与三方、Push、运营配置化等，按实际需求排期，不堆一次做完。

按上述**务实优先级**做，先跑通、再迭代，避免过度设计与理想化。
