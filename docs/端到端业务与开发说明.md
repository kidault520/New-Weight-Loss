# 端到端业务目标与开发说明（简版）

本文档基于产品目标做一次 **对齐说明**：先统一「最终要什么」，再列出 **环境/配置原则**（避免开发环境写死导致无法联调），最后给出 **全链路检查视角** 与 **AI 数据范围**，便于排期与查漏补缺。

---

## 1. 最终业务目标（你描述的需求，整理为一条链）

| 阶段 | 能力 |
|------|------|
| **B 端 / 运营** | 能录入**商品/套餐**等基础数据，并能在后端完成 **订单创建**（依赖产品数据就绪）。 |
| **用户侧** | 注册、登录、**收验证码**；能**看到订单**；能**完整支付**并**开启服务**；能选 **服务开始时间**。 |
| **配送** | 能 **添加/修改地址**；在约定时间、约定地点可感知 **配送状态**；最终 **收到餐**。 |
| **App 内体验** | 通过 **AI 聊天**完成 **餐食热量等待确认记录**；**日反馈**可把行为与数据交给 AI；数据可被 **分析**；能展示 **今天会吃什么**。 |

以上为 **目标态**；当前仓库各模块完成度不同，需按下面「检查视角」逐项对照，而不是假设已全部打通。

### 1.1 业务顺序：支付、开启服务、地址与配送计划

以下顺序与「是否先填地址」**无冲突**：**支付完成**只表示订单已付费，不要求此时已填配送地址。

1. **下单并支付成功**：订单进入已付费状态；可与地址、配送计划配置**解耦**。
2. **开启订单服务**：仅当用户 **已有订单且已付费** 后，才允许开启服务（进入可配置配送计划等后续环节）。
3. **配置配送计划**：在开启服务后的流程中，用户 **填写新地址** 或 **选用此前（无订单时）已保存的地址**，此时地址与计划才对配送生效。

实现与联调时：**向运力下发配送单（`createDeliveryOrder`）** 的合理触发点应在 **配送计划与地址数据就绪** 之后（例如保存计划或开启服务时），而非支付回调瞬间单独承担。

---

## 2. 开发环境配置原则（不要写死）

为满足 **登录、验证码、支付、配送联调**，请遵守：

1. **所有密钥、URL、项目 ID** 放在 **`.env` / Supabase Dashboard / Edge Secrets**，代码里 **禁止** 写死生产地址或密钥（已存在的示例仅作占位）。
2. **前端**：`VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY` 指向你的 Supabase 项目；本地 API 代理见 `vite.config.ts`（如 `/api` → `localhost:3001`）。
3. **Node 后端** `project/server`：`PORT`、JWT、`SUPABASE_*`、短信/支付相关占位按 **`.env.example`** 与 `server/.env` 配置。
4. **验证码**：依赖 **短信/OTP 提供商** 与 Supabase Auth 或后端 OTP 逻辑；**开发环境**常见做法是：控制台看码、或 Supabase **Auth 测试邮箱**、或后端 **OTP 降级到内存**（见 `otpStore` 等），**不要**在 README 里写死「只能用某一个号」。
5. **支付**：聚合/沙箱 URL、回调地址应可配置；**规则**见 `.cursor/rules/third-party-aggregation.mdc`（主路径 webhook/聚合，避免单厂商写死主流程）。
6. **Edge 函数**（如 `ai-chat`）：`DeepSeek_API_KEY` 等放在 **Supabase Secrets**，部署后生效；改代码需 `supabase functions deploy`。
7. **地图选点**：`VITE_AMAP_KEY`（及可选 `VITE_AMAP_SECURITY_JS_CODE`）见项目根目录 `.env.example`；高德控制台需绑定前端访问域名；数据库需含 `delivery_addresses.latitude/longitude`（见对应 migration）。

**结论**：本地要「能登录测试」，**必须**同时满足：环境变量齐全、Supabase 项目与迁移、**Node 后端**（若登录/订单走 `/api`）、**必要时 Edge 已部署**。

## 3. AI 聊天与日反馈 — 数据范围（你补充的「最终反馈」）

目标：**不是**只聊一句话，而是 AI 在对话中能调度 **与「今日日反馈」一致的全量行为与数据**，并具备 **真伪/一致性** 与 **实时性** 意识。

| 维度 | 应包含（目标） |
|------|----------------|
| **行为** | 日反馈中的：已摄入餐、补剂、任务等（含完成/未确认状态）。 |
| **数据** | 「已记录数据」：**AI 快捷卡片待确认并写入的**、**用户手录的**、**设备同步的**；并与 **历史数据** 结合：**引导页/问卷报告**、**基础信息（profile）** 等。 |
| **能力** | 对异常与来源有 **识别与约束**（不瞎编）；能配合 **调度与记录**（如确认、快照、健康档案）；**实时沟通**输出（受 Edge 提示词与 `health_records` / 快照限制）。 |

**实现上**：当前以 **Supabase `health_records` + `chat_messages` + `buildDailyAdvisorSnapshot` + `user_profiles`** 等为组合；**完整**达到上表，还需在 **数据聚合层** 明确：设备数据入口、日反馈统计与 AI 快照字段 **一一对应**，并在文档/代码中避免缺口。

**专项说明**：更细的聊天消息与绿色反馈规范见 **`AI聊天与反馈-标准说明.md`**。

## 4. 全链路检查视角（前后端问题梳理用）

按模块列出 **问题形态**，便于排期；不代表现状已全部故障。

### 4.1 管理端 / 商品 / 订单

- 商品、套餐、价格、销售配置等 **是否仅 B 端可录入**、与 **订单行** 是否一致。
- 订单状态机：**待支付 → 已支付 → 服务中 / 待配送** 等是否与 **App 端展示**、**执行计划** 一致。

### 4.2 认证与验证码

- 注册/登录走 **Supabase Auth** 还是 **Node `/api/auth`**，需与 **前端** 统一。
- 验证码 **发送失败**、**频率限制**、**开发环境** 降级策略是否可测。

### 4.3 支付

- 回调 URL、签名、订单幂等；**沙箱** 与 **生产** 分离；**不要**把支付 URL 写死在前端业务逻辑。

### 4.4 服务开启 / 开始时间 / 执行计划

- `payment_time` / `start_time` 与北京日对齐（多处业务已强调**北京日**）。
- 开启服务后 **计划天数、阶段、餐次** 是否与 **订单/合同** 一致。

### 4.5 地址与配送

- `delivery_addresses`、`delivery_schedules`、**餐次绑定地址**、**锁定窗口**。
- 聚合配送 **回调**（见 `deliveryCallbacks`、规则文档）与 **状态回写**。
- 用户端 **在特定时间/地点看到状态** 依赖 **调度数据 + 前端展示**，需联调。

### 4.6 今日餐食 / 热量 / 日反馈

- **今日吃什么**：来自 **排期/套餐/快照** 与 **健康档案** 是否一致。
- **热量记录**：快捷卡片 → 确认 → `health_records`；**日反馈** 统计与 **AI 快照** 同源校验。

### 4.7 AI

- Edge **`ai-chat`**：提示词、快照、**短答/长答** 策略；部署与密钥。
- **真伪**：靠 **快照 + 库表数据**，禁止模型编造；缺口需 **补数据链** 而非只改文案。

### 4.8 前端工程

- **多入口**：用户端 `npm run dev`、管理端 `admin`、`server`；代理与 CORS。
- **环境**：`.env` 与 `import.meta.env` 勿提交真实密钥。

---

## 5. 建议的本地开发启动顺序（最小可测）

1. 配置 Supabase 与 `project/.env`、`project/server/.env`。
2. 执行必要 **migrations**（Supabase SQL / CLI）。
3. `server`：`npm start` 或 `npm run dev`（端口与前端代理一致）。
4. 用户端：`npm run dev`；管理端：`admin` 下 `npm run dev`。
5. 若测 AI：**部署** `ai-chat` Edge 并配置 Secrets。
