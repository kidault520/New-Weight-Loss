# 上线前必修清单（P0/P1，10条）v1.1

## 说明

- 本清单用于上线前“必须完成”的技术与业务链路验收。
- 分级：
  - `P0`：阻断级，不通过不得上线。
  - `P1`：高风险，建议上线前完成，最迟灰度前补齐。
- 每条均包含：验证方式、通过标准、预计改动范围。

---

## P0（必须先过）

### 1. 关闭生产“模拟确认支付”入口 ✅ 已完成

- **问题**：存在可将订单直接置为已支付的模拟接口路径。
- **验证方式**：生产配置下调用 `POST /api/orders/:id/confirm-payment`。
- **通过标准**：生产环境不可用（返回 403/404 或显式禁用）；仅开发/测试环境可用且有开关保护。
- **预计改动范围**：`server/routes/orders.js`，环境变量与部署文档。
- **验收证据**：
  - 门禁结果包含 `route.confirm_payment.guarded` 绿项（严格模式）。
  - 验证命令：`npm run predeploy:check`、`cd server && npm run predeploy:check`。

### 2. 主订单链路接入“创建支付单” ✅ 已完成

- **问题**：主动创建支付单未完整接入主业务订单流程。
- **验证方式**：新建订单后检查日志/数据库/三方请求记录。
- **通过标准**：订单创建后可追踪支付单创建成功；失败有重试与错误可观测。
- **预计改动范围**：`server/routes/orders.js`，`server/services/paymentProviderService.js`。
- **落地说明**：
  - 新增用户主链路接口：`POST /api/orders/:id/create-payment`。
  - 在 `confirm-payment` 前置调用支付单创建（含重试、审计日志、错误码）。
  - 前端 `src/services/paymentService.ts` 已切到“先创建支付单，再确认支付”流程。

### 3. 主订单链路接入“创建配送单” ✅ 已完成

- **问题**：主动下发配送单未完整接入主业务订单流程。
- **验证方式**：订单进入配送阶段时检查 outbound 请求与回执。
- **通过标准**：可获得运单/任务编号；失败有重试与告警；订单状态与配送状态一致。
- **预计改动范围**：`server/routes/orders.js`，`server/services/deliveryProviderService.js`。
- **落地说明**：
  - `POST /api/orders/:id/start-service` 已接入 `createDeliveryOrder`。
  - 严格模式下下发失败会阻断开启服务并返回 `DELIVERY_CREATE_FAILED`。

### 4. 统一 Edge Function 鉴权客户端写法 ✅ 已完成

- **问题**：不同函数 Supabase 客户端初始化不一致，可能引发鉴权/RLS行为差异。
- **验证方式**：同一用户在相关函数执行鉴权查询，比较返回一致性。
- **通过标准**：统一为 `anon key + Authorization header` 模式；RLS口径一致。
- **预计改动范围**：`supabase/functions/analyze-diet/index.ts`，`supabase/functions/analyze-hrv/index.ts`（并与 `analyze-glucose` 对齐）。
- **验收证据**：`analyze-diet`、`analyze-hrv`、`analyze-glucose` 均为 `anon key + Authorization` 初始化口径。

## P1（高优先）

### 5. 短信生产链路打通（禁止生产 mock 兜底） ✅ 已完成

- **问题**：生产环境若非 webhook 提供商，验证码发送不可用。
- **验证方式**：生产参数下实发短信验证码。
- **通过标准**：`SMS_PROVIDER=webhook` 可成功发送；失败有明确错误码与可观测日志；无隐式 fallback。
- **预计改动范围**：`server/services/smsService.js`，部署环境变量配置。
- **落地说明**：
  - `server/services/smsService.js` 在生产下禁止 mock 兜底。
  - `server/.env.production.template` 已给出 webhook 生产模板字段（示例值占位）。

### 6. 配送状态映射修正（provider 命名一致） ✅ 已完成

- **问题**：部分 provider 命名与状态映射规则键不一致，可能落入错误状态。
- **验证方式**：回放真实回调样例（含 `sf_city` 等）。
- **通过标准**：状态按 code/text 正确映射，不落入 `fallback_pending`。
- **预计改动范围**：`server/config/deliveryStatusMapping.js`，`server/services/deliveryProviderService.js`。
- **落地说明**：
  - 增加 provider 别名归一：`sf_city/sf_openic/sf_express/shunfeng -> sf`。
  - 新增后端测试：`server/tests/deliveryStatusMapping.test.js`。

### 7. 聊天“配送时间”口径与全局常量统一 ✅ 已完成

- **问题**：聊天快捷文案中的配送时间与全局配置不一致。
- **验证方式**：触发聊天快捷动作“配送时间”，对比 `deliveryMealTimes`。
- **通过标准**：聊天回复时间窗口与全局常量一致，仅保留单一口径。
- **预计改动范围**：`src/hooks/useChatLogic.ts`，`src/constants/deliveryMealTimes.ts`。
- **落地说明**：`useChatLogic` 已改为读取 `getDeliveryMealTimeRange('lunch'|'dinner')`，移除硬编码时间。

### 8. 去除误导性 mock 数据（或显式演示标识） ✅ 已完成

- **问题**：部分页面在主流程中使用 mock/随机数据，易被误解为真实数据。
- **验证方式**：未接真实数据时巡检配送计划、步数对比等关键界面。
- **通过标准**：要么接入真实链路，要么 UI 明确标识“演示数据/未接入”。
- **预计改动范围**：`src/services/deliveryPlanService.ts`，`src/components/StepsDetailScreen.tsx`，相关 UI 文案组件。
- **落地说明**：
  - 配送计划增加 `is_demo_data` 字段，餐名标识 `演示数据·...`。
  - 步数对比去随机化改为稳定演示值，并在 UI 明示“演示数据”。

### 9. 引导页报告评分可解释性补齐 ✅ 已完成

- **问题**：评分文案、维度描述与算法实现存在理解偏差风险。
- **验证方式**：抽样 3 份报告，逐项核对维度、分值、算法说明。
- **通过标准**：文案与实现一致；评分逻辑可追溯；对外说明可读。
- **预计改动范围**：`src/utils/healthAssessmentScoring.ts`，报告页文案与 `docs`。
- **落地说明**：
  - 新增 `calculateHealthScoreBreakdown`，可输出规则级评分明细。
  - 新增说明文档：`docs/引导页评分口径与算法说明-v1.0.md`。
  - 新增测试：`src/utils/__tests__/healthAssessmentScoring.test.ts`。

### 10. 测试与质量基线建立（前后端） ✅ 已完成

- **问题**：后端测试脚本薄弱，前端测试与 lint 告警量高，关键链路缺少自动化保障。
- **验证方式**：
  - 前端：`npm run test -- --run`，`npm run lint`
  - 后端：可执行的 `server` 测试脚本（非占位）
- **通过标准**：关键链路（支付、配送、聊天意图、评分）具备可运行测试；后端测试命令可执行；lint/测试达到团队设定阈值。
- **预计改动范围**：`package.json`，`server/package.json`，`src/services/__tests__`，`server/tests`。
- **当前基线**：
  - 前端测试：`15` files / `123` tests 全通过。
  - 前端 lint：`npm run lint` 通过。
  - 后端测试：`node --test tests/*.test.js` 全通过（`5` tests）。
  - 发布门禁：根目录与 `server` 均可执行 `predeploy:check`，`red=0`。
