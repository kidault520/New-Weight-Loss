## A. 餐食三线：MTP（疗程）/ MS（排期模板）/ `delivery_schedules`（履约）

**职责划分（产品共识）**

- **配送计划**（`meal_plan_config` + 写入 `delivery_schedules` 的槽位）：只承载 **用户信息、配送日、餐次、地址**（以及锁定/快照等履约字段）。不要求与排期模板 **按日按餐次一行一行对齐**。
- **排期模板 / `meal_schedule_entries`**（经 `active-meal-schedule`）：承载 **日历上的日期与套餐、菜品内容**——用户端「今日吃什么」应以此为准，而不是从 `delivery_schedules` 反推菜品。

因此：**「模板里某天有午餐」与「用户表里某天有午餐配送行」不一致，在设计上可以成立**；治理重点是 **UI 与接口不要混用数据源**（例如用 delivery 行去猜菜品），而不是强行做库表级强制一致。

| # | 检查项 | 在本项目中的落点 / 说明 |
|---|--------|-------------------------|
| A1 | 商品 `duration_days` 是否与餐食疗程 `meal_plans` 结构一致 | `server/routes/admin/products.js` 中疗程天数校验；订单侧 `src/services/orderMealPlanSlots.ts` 使用 `products.meal_plans.included_meal_types` |
| A2 | 订单快照餐次 vs 商品疗程餐次谁优先、是否可追溯 | `fetchMealSlotsEnForOrderId` / `fetchLatestPaidOrderProductMeta`：优先 `orders.included_meal_types`，否则回落 `meal_plans`；需确认改商品后老订单行为是否符合产品预期 |
| A3 | 启用中的 MS 是否唯一、周视图日期是否对齐 | 管理端 `server/routes/admin/menu.js`（`meal_schedules`）；C 端 `src/services/activeMealScheduleService.ts` → `GET /delivery-schedules/active-meal-schedule` |
| A4 | 今日排期展示是否走「排期 API」而非直连 MTP | `TodayMealsCard` 使用 `activeMealScheduleService`；与脑图一致：MTP 不直连排期模板，用户侧展示以 **启用模板 + 实例化结果** 为主 |
| A5 | `delivery_schedules` 行是否覆盖用户所选配送日与餐次 | 生成与同步：`App.tsx`（配送计划写入 `delivery_schedules` 相关逻辑）；`server/routes/deliverySchedules.js`；迁移 `20260324000000_unify_delivery_schedules.sql` 等 |
| A6 | 两链数据是否被错误混用（非强制对齐） | **不要求** entries 与 `delivery_schedules` 行级一致。抽查：前端/接口是否在展示菜品时误用 delivery 表；支持/运维需要时可对比两源以解释用户疑问 |
| A7 | 改址、锁定、审计后 **delivery 履约行**是否符合治理规则 | 与 MS 是否「同日有餐」无强制关系；查快照、`is_locked`、RLS 等：`20260328000000_delivery_governance_p0_p1.sql`、`20260328010000_delivery_schedule_data_guards.sql` 等 |

**可选端到端理解样本**：同一用户、同一北京日，分别看清四者**职责**（不必行级相等）：商品侧 `meal_plans`、启用 `meal_schedules`、`GET active-meal-schedule`（内容）、`delivery_schedules`（槽位）。

## B. `meal_plan_config` 与库表「双源」治理

| # | 检查项 | 在本项目中的落点 / 说明 |
|---|--------|-------------------------|
| B1 | 主数据存储位置 | `src/services/mealPlanConfigService.ts`：`user_profiles.meal_plan_config_data`、`meal_plan_configured`；未登录时 `userStorage` 兜底 |
| B2 | 与配送计划 UI 是否同源 | `App.tsx` 用 `mealPlanConfig` 恢复 `deliveryPlanStartDate` / `endDate` / `selectedDates`；若只改库表不改 profile，易产生漂移 |
| B3 | `TodayMealsCard` 数据源优先级 | `mealPlanConfig` 为空时 `getMealPlanConfig(user.id)`；有订单时依赖 `activeMealScheduleService` → 需书面约定 **无订单 / 有订单 / 仅有 config** 三态优先级 |
| B4 | 餐次列表是否双源冲突 | `meal_plan_config.selectedMealTypes` vs 订单 `included_meal_types` / `meal_plans.included_meal_types`（见 `orderMealPlanSlots.ts`） |
| B5 | 写回时机是否完整 | `saveMealPlanConfig` 是否在「保存配送计划」等关键路径必调用；是否存在只写本地或只写部分字段的分支 |

**治理方向**：`meal_plan_config` 与 `delivery_schedules` 负责 **履约槽位**；**菜品内容**以启用 MS / `active-meal-schedule` 为准。保存配送计划时写回 profile 并同步 delivery 行，但不必校验「必须与当日 MS entries 同构」。

## E. 静代码审查结果（2026-03-24）

以下为基于当前仓库的**静态代码路径核对**，未连真实数据库跑 SQL；结论用于指导联调与抽样验收。

### E1. 总览

| 类别 | 结论 | 说明 |
|------|------|------|
| A 三线 | **MS 内容链**与 **`delivery_schedules` 槽位链**分源，**符合产品设计** | 配送计划 ≠ 排期内容；不要求行级对齐 |
| B 双源 | `meal_plan_config` 与订单餐次、MS 之间仍可能口径不一 | 需各界面明确「管槽位」还是「管菜品/合约餐次」 |
| C 补剂 | 多单时已有明确排序与 `is_active` 过滤；`active-supplement-stage` 取最近一条 `supplement_schedules`（`course_id = supplement_plan_id`） | 边界见 E4 |

### E2. A 类：MTP / MS / `delivery_schedules`

1. **`GET /delivery-schedules/active-meal-schedule`**（`server/routes/deliverySchedules.js`）  
   - 读 **`meal_schedules`（is_enabled）** + **`meal_schedule_entries`** + 套餐/菜品。  
   - 调用前执行 **`syncMealScheduleActivation`**（`server/services/mealScheduleActivationService.js`），按**北京日历日**与 `start_time`/`end_time` 切换唯一启用排期。  
   - **结论**：用户端「今日吃什么」来自 **MS 模板实例**，与 MTP 无直接 JOIN（符合脑图）。

2. **`delivery_schedules` 餐食行如何生成**  
   - `deliveryScheduleService.syncUserDeliverySchedules` 仅根据入参 **`items: { date, mealType, addressId }[]`** upsert，**不读取** `meal_schedule_entries`。  
   - 主路径：`App.tsx` → `handleDeliveryPlanComplete` → 用户勾选的 **`datesToSync` × `mealTypesToSync` × `mealAddresses`** → `saveMealPlanConfig` + `syncUserDeliverySchedules`（约 2094–2114 行）。  
   - **结论（与产品一致）**：这是在写 **履约槽位**（用户、时间、餐次、地址）。**排期里的日期与套餐内容**由 MS / `active-meal-schedule` 提供，用于 **展示吃什么**。两源 **不必** 在「某日是否有午餐行」上与 entries 强制一致；需避免的是产品/前端把「有没有 delivery 行」当成「有没有排期菜品」。

3. **北京周界**（`server/utils/timezone.js` → `getBeijingWeekRange`）  
   - **已修复**：按北京日历计算周一～周日（`addDaysToBeijingYmd` + `T12:00:00+08:00` 锚点），不依赖 Node 本地 `getDay()`；`deliverySchedules` 路由引用该公共函数。

### E3. B 类：`meal_plan_config`

- **写入**：`handleDeliveryPlanComplete` 内 `saveMealPlanConfig(userId, config)` 与 `syncUserDeliverySchedules` 同事务意图上连续，但后者失败会抛错（约 2116–2119 行），需确认 UI 是否回滚 profile 侧认知。  
- **读取**：`App.tsx` 多处用 `mealPlanConfig` 恢复配送日历；`TodayMealsCard` 用 **context 的 `mealPlanConfig` 或 `getMealPlanConfig` 兜底**，菜品内容仍走 **active MS**。  
- **结论**：**B3/B4**：三处口径并存已在代码中 **JSDoc 标明分工**（`orderMealPlanSlots.ts`、`TodayMealsCard.tsx`）；产品层若需强制一致再定规则。

### E4. C 类：多补剂

- **`pickSupplementFulfillmentOrder`**：`processing` > `confirmed` > `pending` > 其它，同档按 `payment_time`/`created_at`；跳过 `supplement_plans.is_active === false`。  
- **`GET .../active-supplement-stage`**：订单列表窗口已放宽为 **`SUPPLEMENT_ORDER_QUERY_LIMIT`（100）**（原为 50），与排序挑选范围对齐。  
- **`supplement_schedules`**：`course_id = orderProduct.supplement_plan_id`，`limit(1)` + `created_at` 倒序——若历史重复 course 多行，需依赖 DB 唯一约束与迁移保证。

### E5. 建议的下一步（可执行）

| 动作 | 说明 |

| （可选）客服对账 | 仅在用户质疑时，对比同一北京日 entries 与 delivery 行，解释「槽位」与「排期内容」分工 |

## G. 历史餐食 `syncId` 一次性策略（迁移说明）

- **Supabase 网页 SQL Editor**：分步语句见 **`supabase/manual/backfill_legacy_food_syncid_supabase_dashboard.sql`**（先 ① 条数、② 样本、再 ③ `UPDATE`）。
- **目的**：旧版完成摄入写入的 `health_records` 无 `syncId`，新逻辑下会全部计入「加餐」。迁移仅对 **高置信度** 行补 `syncId`，使其在 **日反馈 / 营养详情** 中回到对应早/午/晚。
- **条件摘要**：`mealType` ∈ 早午晚（中英）；`source <> 'ai'`；`name` 匹配「早餐|午餐|晚餐」或「餐别：…」等客户端形态。
- **未命中**：仍为加餐展示；或属真实手动/AI，无需改。
- **回滚**：见迁移文件内注释（`nutrition_data - 'syncId'` 且 `syncId LIKE 'legacy-intake-%'`）。
