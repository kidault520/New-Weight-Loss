# 地址相关规则总规范（v1.5）

## 1. 文档目的

本文件是“地址新增/查询/编辑/删除”的统一执行规范，覆盖前端交互、服务层校验、数据库约束、异常处理与验收标准，作为后续开发与回归唯一口径。

---

## 2. 适用范围

### 2.1 入口与模块

- 页面入口：`AddDeliveryAddressPage`
- 表单组件：`AddressForm`（页面态/弹层态共用规则）
- 前端业务：`useAddressManagement`
- 服务层：`addressService`

### 2.2 数据表

- `delivery_addresses`：地址主表（软删除）
- `delivery_schedules`：配送执行数据（在用与锁窗判断）
- `delivery_audit_logs`：地址审计日志

---

## 3. 数据字段规则（强制）

### 3.1 必填字段

- `address`（地址）
- `doorNumber`（门牌号）
- `name`（联系人）
- `phone`（手机号）
- `tag`（标签）

### 3.2 手机号规则

- 输入限制：只允许数字，最多 11 位
- 业务正则：`^1[3-9]\d{9}$`
- 失败提示：`请输入有效的手机号码`
- 数据库约束：仅对激活地址生效（`is_deleted=false`）

### 3.3 标签规则

- 标签必填，且保存前必须 `trim`
- 同一用户“激活地址”内标签唯一（大小写不敏感 + trim 后比较）
- 编辑当前地址时允许保留原标签
- 自定义标签删除规则：
  - 被任一地址使用：不可删
  - 未被任何地址使用：可删

### 3.4 数据归一化规则

- 标签读写统一 `trim`
- 标签比较统一 `lower(btrim(tag))`
- 历史兼容：编辑回填优先 `tag`，兼容旧字段 `label`

---

## 4. 默认配送地址规则（全部/餐次）

### 4.1 交互规则

- 页面直接展示 `全部/早餐/午餐/晚餐`，不使用折叠交互
- 点击餐次即为该地址声明默认餐次
- 取消最后一个餐次时，该地址退出默认状态

### 4.2 排他规则

- 同一餐次同一时刻只能有一个默认地址
- 选中某地址后，需从其他地址剔除冲突餐次
- 某地址餐次被剔空后，自动 `is_default=false`

### 4.3 “全部”规则

- 仅在 `早餐/午餐/晚餐` 均未被其他地址占用时可选
- 选中“全部”等价于该地址占用全部餐次

## 5. CRUD 流程规范

### 5.1 Create（新增）

1. 前端先做必填/手机号/标签唯一校验
2. 调用 `addressService.createAddress`
3. 若设置默认餐次，执行餐次排他清理
4. 刷新地址与配送计划相关缓存
5. 写入审计日志（`create`）

### 5.2 Read（查询）

- 查询条件：`user_id + is_deleted=false`
- 排序建议：默认地址优先，其次创建时间倒序
- 旧数据兼容：缺历史字段时可降级读取，但不影响主流程

### 5.3 Update（编辑）

1. 编辑前检查“今日配送前 1 小时锁定窗口”
2. 使用 `updated_at` 乐观锁避免并发覆盖
3. 同步未来可改配送计划地址快照（锁窗内餐次跳过）
4. 若默认餐次变更，执行排他清理
5. 写入审计日志（`update`）

### 5.4 Delete（删除）

1. 删除前检查是否被未来配送计划使用
2. 在用地址禁止删除并给出提示
3. 非在用地址软删除：`is_deleted=true, deleted_at=now`
4. 写入审计日志（`soft_delete`）

## 6. 数据库硬约束（最终口径）

### 6.1 已落地约束

- `delivery_addresses_tag_required`
  - 规则：激活地址标签不能为空
- `delivery_addresses_phone_cn_valid`
  - 规则：激活地址手机号必须匹配 `^1[3-9][0-9]{9}$`
- `idx_delivery_addresses_user_tag_unique_active`
  - 规则：同一用户激活地址标签唯一（`lower(btrim(tag))`）

### 6.2 迁移链路

- `supabase/migrations/20260328060000_address_data_constraints.sql`
  - 首版约束迁移（`NOT VALID` + 条件 `VALIDATE`）
- `supabase/migrations/20260328062000_address_constraints_active_only_fix.sql`
  - 约束范围修正为仅激活地址，兼容历史软删除脏数据
- `supabase/migrations/20260328064000_address_unique_tag_backfill_and_index.sql`
  - 回填重复标签（每组保留 1 条，其余软删除）并补建唯一索引

### 6.3 当前验收状态

- `delivery_addresses_tag_required`：`convalidated=true`
- `delivery_addresses_phone_cn_valid`：`convalidated=true`
- `idx_delivery_addresses_user_tag_unique_active`：应存在且可用

## 7. 异常与处理策略

- `CHECK` 失败（`23514`）：
  - 先按激活地址范围排查脏数据，再修复或软删除后 `VALIDATE`
- 唯一索引创建失败（重复标签）：
  - 先做重复组回填，再建索引
- 锁窗内编辑：
  - 直接拦截，提示不可修改
- 在用地址删除：
  - 直接拦截，提示不可删除

---

## 8. 回归测试清单（发布最小集）

1. 空标签保存失败（前端 + 后端）
2. 非法手机号保存失败（前端 + 后端）
3. 重复标签保存失败（服务层 + 唯一索引）
4. 编辑时标签高亮与实际值一致（含空格场景）
5. 在用标签不可删，未用自定义标签可删
6. 默认地址餐次排他正确（含“全部”互斥）
7. 在用地址不可删除，非在用地址软删除成功
8. 锁定窗口内编辑被拦截
9. 审计日志写入完整（create/update/soft_delete）
10. 约束与索引巡检结果为 PASS

补充：可直接使用 `docs/sql/address-governance-smoke-check.sql` 做一键巡检。

## 9. 配送地址补丁说明（v1.5 新增）

### 9.1 补丁目标

本补丁聚焦“默认餐次变更导致配送计划体验不一致”的问题，目标是：

- 编辑地址后不再无条件打断用户流程
- 对“餐次覆盖不完整”给出前置、可理解提示
- 在生成配送计划环节做硬校验，禁止带缺口提交

### 9.2 触发规则（管理模式）

#### A) 编辑已有地址（Update）

- 地址保存成功后：
  - 同步未来且可修改的配送快照（锁窗内跳过）
  - 不再强制弹出“前往配送计划”确认框
- 若保存后发现“订单餐次存在未覆盖缺口”：
  - 弹出告警：`地址已保存，但餐次未覆盖完整`
  - 明确提示缺失餐次（如：早餐/午餐）
  - 引导用户“新增地址并补齐餐次”，否则后续生成会被拦截

#### B) 新增地址（Create）

- 仅当“新增地址包含默认餐次”时，才建议用户前往重新生成配送计划
- 若新增后仍有餐次覆盖缺口，优先提示“缺口告警”，不再直接引导重配

### 9.3 强校验口径（DeliveryPlanPage）

- 点击“生成配送计划 / 确认配送计划”时：
  1. 先检查 `dateMealConfigs` 是否加载完成（未完成则提示“请稍候”）
  2. 再检查是否存在 `addressId` 为空的餐次配置
  3. 若存在缺失，直接阻断提交并提示：
     - 标题：`地址配置不完整`
     - 内容：`以下餐次缺少配送地址：... 请新增地址，或在默认地址中补齐对应餐次后再生成配送计划。`

> 说明：该拦截为硬校验，防止“用户只给部分餐次配置默认地址”导致隐式兜底和错误排期。

### 9.4 时间锁窗与同步边界

- 地址编辑后的快照同步只作用于：
  - 今日及未来、且状态可更新的餐次
- 今日若已进入配送前 1 小时锁窗，或已过配送开始时间：
  - 该餐次不会被回写
  - 会计入“跳过锁定餐次”统计

### 9.5 用户可见反馈口径（统一文案）

- 编辑成功且有同步统计：
  - `地址已更新，已同步 X 个可修改餐次（跳过 Y 个锁定餐次）`
- 保存后覆盖不完整：
  - `地址已保存，但餐次未覆盖完整`
  - `当前缺少默认地址的餐次：... 请新增地址并补齐对应餐次；否则生成配送计划时会被拦截。`
- 生成时硬拦截：
  - `地址配置不完整`
  - `以下餐次缺少配送地址：...`

### 9.6 验收用例（补丁专项）

1. 原本“午餐+晚餐”共用地址，编辑后仅保留“午餐”：
   - 不强跳“前往配送计划”
   - 立即出现“缺少晚餐地址”的告警
2. 不新增任何地址，直接去生成配送计划：
   - 命中“地址配置不完整”并被阻断
3. 新增一个仅覆盖缺失餐次的地址后再次生成：
   - 不再拦截，允许继续生成
4. 今日已过配送开始时间的餐次：
   - 不应触发“1小时锁窗拦截”误报
   - 不应参与可编辑同步集
5. 新增带默认餐次地址（且无缺口）：
   - 可出现“建议前往配送计划重新生成”
